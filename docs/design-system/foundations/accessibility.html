Foundation

Accessibility

TwinkleTune is built for children from five years old, some of whom cannot read yet, some of whom use a switch or a screen reader, and all of whom deserve to feel good about singing. Every component meets WCAG 2.2 AA, and the system adds commitments of its own for children.

Overview

Accessibility here is by construction: tokens are chosen so the contrast pairs pass in both themes, components ship with their keyboard model and labels, and the checker scripts catch the mechanical slips. This page is the list every component page's #accessibility section answers to.

  • WCAG 2.2 AA commitments, criterion by criterion, as TwinkleTune keeps them.
  • Commitments for children that go beyond WCAG: no colour-only feedback, no timers that punish, no failure language.
  • The interaction tokens this page owns: focus ring, target sizes and control heights.
  • The component contract and the testing procedure.

Commitments for children

WCAG is the floor. These are the promises a singing app for small children makes on top of it, and every new string, colour and animation is checked against them.

  • No colour-only feedback. A landed note turns gold and a cheer pops (Perfect! ✨); a selected card says SINGING NOW ⭐; stars come with "2 stars earned". A child who cannot tell gold from blue loses nothing.
  • No failure colour, sound or icon. No red, no crosses, no buzzer. A note that slips by simply stays blue. Pink is the gentlest nudge there is and always says what to try next.
  • No timers that punish. Nothing times out on a child. Silence is not a wrong note: Find My Voice waits as long as she needs, the Sing screen keeps going whether she sings or not, and the parent gate never locks.
  • No failure language. No "wrong", "missed", "failed", "try harder" or "game over". Every result headline is praise (Super / Beautiful / Brave Singing), and a tricky part is an offer, never a penalty. See Content.
  • Never show an error to a child. Server problems fall back to the bundled songs and cached data with a calm note (Offline songbook — duets and family scores come back when the server does.) and a way to keep singing.
  • Pre-readers can play. Every action has an emoji and sits in the same place on every screen; the one big obvious action is always the largest thing in reach.
  • Big targets, generous gaps. 52px minimum for anything a child taps, 8px or more between neighbours.
  • Calm motion. Slow, decorative loops that stop under reduced motion; nothing flashes.
  • Grown-up actions are fenced. Destructive and settings actions sit behind the parent gate so a curious tap cannot erase a singer.
  • Privacy is accessibility too. No account, no sign-in, nothing to remember; singing audio never leaves the device.

Focus

One ring for every interactive element: an outline of --focus-ring-width (3px) in --color-focus-ring, offset by --focus-ring-offset (3px), shown on :focus-visible only. The offset lets the surface show through, so the ring contrasts with both the control and the page. The mocks used the brand blue at 2.6:1 (D21).

  • Use outline, not box-shadow, so the ring survives forced-colours mode (where it becomes Highlight). --shadow-focus exists only for parts that clip outlines.
  • Round controls round their ring (border-radius: 50% on icon buttons).
  • Dialogs move focus to their first action on open and return it to the opener on close.

Target sizes

Three steps. WCAG 2.2 AA asks for 24px; TwinkleTune asks for more wherever a child's finger lands.

Control heights

Buttons and fields share three heights so a field and its button line up in a row.

--control-height-sm, -md and -lg: small toy button and field, the toy button, the extra-large hero button and name input.

The small height (44px) is below the child target, so it appears only in grown-up rows and dialogs. Every child-facing button is medium or larger.

Component contract

Every component page's #accessibility section contains all seven:

  1. Role and pattern: the native element or the WAI-ARIA Authoring Practices pattern it follows, linked.
  2. Keyboard map: a .ds-keys table of keys and effects.
  3. Focus: where it starts, where it goes on close, how the ring looks.
  4. Labelling: what must be named, how, and what a screen reader announces. Decorative emoji hidden.
  5. Contrast: the token pairs involved, live in both themes.
  6. Motion: what animates and what reduced motion does.
  7. Touch: target sizes and the alternative to any hover.

Plus, for TwinkleTune: the encouragement test. Every string and state a child can see is checked against the commitments for children.

Testing procedure

  1. Automated: check_contrast.py for every declared pair in both themes; check_design_system.py for labels, names, alt text, landmarks, headings and links.
  2. Keyboard: Tab through each component page's examples and each mock flow (Welcome → Home → Songs → Sing → Pause → Results). Focus is always visible, never trapped outside a dialog, and returns to the opener.
  3. Screen reader: VoiceOver on iOS (the likeliest device) and NVDA on Windows, on one dialog (Pause), one form (song editor), the Results screen and the high-score table. Emoji are not read twice; star counts and progress are announced as words.
  4. Zoom and reflow: 200% and 400% zoom, and a 320px viewport. See Responsive.
  5. Preferences: emulate prefers-reduced-motion, prefers-contrast: more and forced-colors: active.
  6. Encouragement read-through: read every new child-facing string aloud as if to a five-year-old who just sang badly. If it stings, rewrite it.
