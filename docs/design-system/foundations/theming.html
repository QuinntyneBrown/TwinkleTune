Foundation

Theming

TwinkleTune ships one theme, the daytime sky studio. The night studio is fully defined in the tokens and drawn in every mock, but the app does not implement it yet. Both run on the same three tiers of tokens, so a theme is a set of semantic overrides and nothing else.

Overview

  • Sky studio (light) is the product as it ships: a pale-blue daytime sky, white cards, a blue toy button and gold sparkles. It is :root.
  • Night studio (dark) is the same studio after bedtime: a deep navy canvas with surfaces that rise lighter as they come forward (D08), a brand-blue button with navy ink, and the same gold. It exists in tokens.css and in every mock, because each mock must work in both themes. The app does not implement it; whether it ships, and whether it follows the device setting, is an open question in the mocks.

Components never know which theme is active. They read semantic tokens (--color-bg-surface, --color-accent); a theme redefines those tokens and every component follows.

How a theme applies

Three switches, in priority order:

  1. data-theme="dark" on any element applies the night studio to it and everything inside. It works on <html> for a whole page or on a wrapper, which is how this site shows both themes side by side.
  2. data-theme="light" forces the sky studio even when the device prefers dark.
  3. prefers-color-scheme: dark applies the night studio to :root:not([data-theme="light"]) when nothing forces light.

Each theme block also sets color-scheme (light or dark) so native parts (scrollbars, form controls, the date picker, the <dialog> backdrop) match.

:root                     { /* sky studio */   color-scheme: light; }
[data-theme="dark"]       { /* night studio */ color-scheme: dark; }
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { /* night studio, identical to the block above */ }
}

Composite tokens that embed other tokens (the gradients, --shadow-focus) are repeated inside each dark block, because a custom property resolves where it is declared: a nested [data-theme] wrapper has to recompute them.

/* tier 2 */ --color-accent: var(--palette-sky-600);          /* [data-theme="dark"]: var(--palette-sky-400) */
/* tier 3 */ .btn { --btn-bg: var(--color-accent); background: var(--btn-bg); }

Adding a theme

  1. Name it for a time or place in the studio (the house style: sky studio, night studio), and write down why it exists.
  2. Add primitives only if the palette lacks them. New ramps go in tier 1 next to --palette-sky-* and --palette-night-*.
  3. Override every semantic colour, gradient and shadow in a [data-theme="name"] block. Copy the dark block as the checklist; a token you skip silently inherits sky studio.
  4. Repeat the composite tokens (gradients, --shadow-focus) inside the block and set color-scheme.
  5. Add every pair to tokens/contrast-pairs.json runs and pass check_contrast.py for the new theme: 4.5:1 text, 3:1 edges and focus.
  6. Keep the meanings. Gold stays the reward, pink stays gentle, and no theme introduces red for a child.
  7. Export tokens.json again so the new values appear under each token's themes extension, and mock it: every mock must open in the new theme.
[data-theme="sunrise"] {
  --color-bg-canvas: var(--palette-pink-100);
  --color-bg-surface: var(--palette-white);
  --color-accent: var(--palette-sky-600);
  /* …every semantic colour, gradient and shadow… */
  color-scheme: light;
}

Consuming tokens.json

tokens/tokens.json is generated from tokens.css in the W3C Design Tokens Community Group (DTCG) format. It is for tools: native apps, Figma plugins, Style Dictionary, the marketing site's build. The CSS file stays the source of truth; never edit the JSON by hand.

  • Groups follow the token names: color.bg.canvas is --color-bg-canvas, duration.fast is --duration-fast.
  • Each token has $type (color, dimension, duration, cubicBezier …) and $value. Semantic values are aliases in braces, {palette.sky.200}, so tools keep the tier structure.
  • Light values are the defaults. The com.agent-toolkit extension carries the CSS name, the resolved value and every theme override.
"canvas": {
  "$type": "color",
  "$value": "{palette.sky.200}",
  "$extensions": { "com.agent-toolkit": {
    "css": "--color-bg-canvas",
    "resolved": "…",
    "themes": { "dark": { "$value": "{palette.night.900}", "resolved": "…" } }
  } }
}
// Read the night value of a token in a build script
import tokens from "./tokens.json" assert { type: "json" };
const canvas = tokens.color.bg.canvas;
const night = canvas.$extensions["com.agent-toolkit"].themes?.dark?.resolved
           ?? canvas.$extensions["com.agent-toolkit"].resolved;

Usage

  • Components read semantic tokens only. A primitive in a component file is a review comment.
  • Hover and pressed colours are tokens (--color-accent-hover, --color-bg-subtle-hover), never filter: brightness(), which is invisible on pastels and wrong at night (D20).
  • Illustrations follow the theme through CSS classes (Twinkle's .twinkle-body); never bake colours into SVG.
  • Show both themes on every component page and in every mock with .ds-themes or ?theme=dark, even though only one ships.
  • Near-duplicate tints were collapsed during extraction (D09). Reuse the existing role before adding a token.

  • prefers-contrast: more promotes decorative and default borders to --color-border-strong and muted text to default ink, in any theme.
  • forced-colors: active hands the focus ring and borders to the system colours (Highlight, CanvasText). Never carry meaning by background colour alone; it disappears in this mode.
  • Theme switching never moves layout or changes sizes, so zoom and reflow behave the same in both studios.

Tokens

Theming owns no tokens of its own: a theme is a set of overrides of tokens documented elsewhere. See colours and gradients on Color, shadows on Elevation, and the full file in tokens/tokens.css.
