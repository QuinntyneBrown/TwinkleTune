Architecture assessment · Audio engine

Pitch detection, tuned for reality.

TwinkleTune has a compact, privacy-aligned pitch path that works for clean tones. The next step is to make timing, confidence, and scoring independent of display frame rate, device gain, and the app’s own speaker output.

On-device audio 3 consumers 9 architecture findings 5 delivery phases

01 · Outcome

Executive summary

The current implementation is a credible product prototype. It combines a McLeod pitch estimator, level and clarity gates, median smoothing, octave-forgiving scoring, microphone cleanup, and a no-microphone fallback in about 80 lines of detector code.

Recommended direction. The first milestone should establish repeatable signal and device measurements. The second should separate capture, estimation, temporal filtering, and consumer policy. Algorithm replacement, fixed threshold changes, and acoustic echo cancellation should follow only when the baseline data shows which change is justified.
P0 Speaker-bleed experiment

The guide melody and raw microphone form a plausible false-score path that current tests cannot reproduce.

rAF Logic clock today

Detection, stability capture, and score accumulation inherit display cadence and render stalls.

0 Direct detector unit tests

The unit suite covers range and scoring rules, while PitchTracker is exercised only through browser flows.

3 Different consumers

Gameplay, vocal-range capture, and the tuner currently share one hard-coded smoothing and gate policy.

Highest unverified product risk. SongPlayer emits an exact target pitch through the speaker while PitchTracker requests microphone input with echo cancellation disabled. The clean oscillator fixture bypasses that acoustic loop. A playback-only negative control on physical devices should precede detector tuning.

02 · Investigation

The assessment traces pitch from browser acquisition to all three consumers, then compares implementation behavior with approved L1/L2 requirements, detailed design pages, unit tests, and Playwright fixtures.

In scope

  • Microphone and shared AudioContext lifecycle.
  • PCM window capture, RMS calculation, pitchy estimation, bounds, and median smoothing.
  • Gameplay timing, latency compensation, octave folding, and note accumulation.
  • Stable vocal-range capture and diagnostic tuner behavior.
  • Automated test realism, architecture boundaries, and traceability.

Evidence limits

  • No physical microphone or supported-device matrix was available.
  • No labelled vocal corpus exists in the repository.
  • Speaker bleed and device-level latency remain hypotheses until Phase 0 measures them.

  • No raw voice recording should enter source control without an approved consent and retention policy.

03 · Baseline

PitchTracker owns acquisition, Web Audio nodes, estimation, rejection, smoothing, and session state. Each screen creates its own tracker and polls read() from a display animation loop.

04 · Preserve

What already works

The improvement should retain the current privacy boundary and user fallback while changing the internal contracts.

Keep

Local processing

Microphone audio stays inside the browser. No detector path calls the API or persists raw audio.

Keep

Audio-clock transport

SongPlayer.currentBeat() derives position from AudioContext.currentTime, which avoids wall-clock drift.

Keep

Octave forgiveness

foldCents() judges pitch class rather than vocal register, matching the product’s child-friendly scoring intent.

Keep

Explicit quality signals

PitchFrame already exposes frequency, floating MIDI, clarity, and level.

Keep

Graceful fallback

Voice setup can defer capture. Gameplay can continue in a no-microphone mode. Permission denial does not block solo play.

Keep

Small dependency surface

The estimator uses one focused dependency, pitchy 4.1.0. A replaceable interface can preserve that simplicity.

05 · Risks

Architecture findings

Each finding separates code-proven behavior from hypotheses that require physical measurement. P0 identifies the first validation or architecture gate, not a confirmed production incident.

F-01 P0

The guide melody forms an untested acoustic feedback path

The player sends tonal output to ctx.destination. The tracker requests unprocessed microphone input with echo cancellation disabled. The resulting speaker-to-room-to-microphone path may produce high-confidence detections at the exact target pitch.

The path is plausible from source inspection, but its severity is not established. The first implementation task should run playback-only negative controls through speakers and headphones at representative volumes.

Evidence: player.ts connects the melody master to the destination. pitch.ts sets echoCancellation: false. fake-mic.ts injects a separate clean oscillator, while Playwright also launches with --mute-audio.
F-02 P0

Display cadence controls audio decisions

Gameplay and voice setup call read() from requestAnimationFrame. Gameplay counts render frames. Stable capture defines hold and dropout windows as frame counts. A 30 Hz, 60 Hz, or 120 Hz display therefore changes elapsed smoothing, hold duration, minimum evidence, and exposure to render stalls.

The render loop should display the latest observation. A fixed-hop audio source should drive logic, and consumer decisions should use timestamps or elapsed duration.

Evidence: sing.ts increments totalFrames and hitFrames in rAF. range.ts uses 40 window frames and 8 silent frames. playwright.config.ts caps workers because rAF starvation makes audio tests flaky.
F-03 P0

The detector has no repeatable signal-quality baseline

The unit suite tests StablePitchCapture after MIDI values already exist and tests scoring after observations already exist. No unit test supplies PCM to the estimator. Browser tests use a loud, steady sine wave and cover permission denial.

A pure estimator boundary and labelled fixture runner should precede threshold, filter, frequency-band, detector, or echo-processing changes. The baseline should report pitch error, octave errors, voiced false positives, detection delay, gaps, and processing cost.

Evidence: 76 unit tests pass, and none reference PitchTracker or PitchDetector. Existing E2E coverage uses FakeMic.
F-04 P1

Temporal history has no age or discontinuity

Rejected frames clear latest but retain the median history. A new note after silence can initially report the prior note. The frame also combines raw hz and clarity with a median-filtered midi, so its fields may describe different pitches.

The observation contract should expose raw and filtered values separately. Temporal state should expire by audio time and reset across silence, source changes, or sequence gaps.

Evidence: pitch.ts updates history only for accepted values and clears it only in stop(). latest = { hz, midi, clarity, rms } mixes raw Hz with filtered MIDI.
F-05 P1

One hard-coded signal policy serves three different jobs

Gameplay favors low delay and reliable onsets. Vocal-range capture favors sustained stability. The tuner favors transparent raw accuracy. All three receive the same 2048-sample window, absolute RMS gate, clarity threshold, broad frequency bounds, and 5-value median.

Capture and estimation should stay shared. Filtering and acceptance policy should be named, configurable consumer profiles backed by the fixture baseline.

Evidence: pitch.ts declares all constants at module scope. Each consumer calls new PitchTracker() without options.
F-06 P1

Async lifecycle state is underspecified

running becomes true only after microphone permission resolves and the analyser exists. Concurrent start() calls can open multiple requests. A stop() during a pending start cannot cancel the request, and a later resolution can attach a stream after teardown.

A microphone session should implement idle → starting → running → stopping, accept an AbortSignal, dispose partially-created resources on every failure, and classify denial, absence, busy-device, and browser-policy errors.

Evidence: PitchTracker.start() guards only this.running. Screen callers use broad catch {} blocks and render every acquisition failure as a microphone-denied path.
F-07 P1

Observations have no audio timestamp or sequence identity

PitchFrame describes signal values but not when the window was captured, how old the result is, or whether it is new. Gameplay aligns the polled result to the current playback beat, then applies one manual millisecond offset.

Each observation should carry the audio-window midpoint, emission time, sequence, window size, and source settings. Scoring should map capture time to the transport before applying a separately stored device calibration.

Evidence: PitchFrame has four signal fields only. sing.ts computes scoreBeat = beat - latencyBeats at poll time.
F-08 P2

Low-level input depends on player and personalization modules

pitch.ts imports the shared context from player.ts and frequency conversion from range.ts. The latter also owns voice-range stability and song transposition. This arrangement hides reusable audio primitives behind feature modules.

A context provider, pitch-unit module, browser capture adapter, pure estimator, and temporal policy should establish inward dependencies. The player and tracker may still share one context through the provider.

Evidence: Imports at the top of pitch.ts and player.ts.
F-09 P2

Requirements freeze constants before quality is measured

Approved L2 requirements prescribe a 2048-sample window, RMS 0.01, clarity 0.8, 70–1500 Hz, five accepted values, 40 range frames, and three scoring frames. These values describe the implementation but do not define device-level error, false positives, onset delay, or fairness across render rates.

The existing identifiers should remain traceable. Their wording should shift toward measurable outcomes after Phase 0, while configuration baselines move to an architecture decision record or tuning profile.

Evidence: AE-L2-10…16, VP-L2-3…4, SR-L2-2, and SG-L2-9.

06 · Direction

Target architecture

The target separates real-time capture from estimation and policy. It lets gameplay consume each unique audio observation while the UI renders the latest state at any display rate.

Audio time is authoritative. Every result carries capture time. Display time never defines hold duration, score evidence, or filter age.
Raw and filtered are explicit. Frequency, MIDI, clarity, and level refer to the same raw window. Filtered pitch appears in a separate field.
Policy follows the consumer. Gameplay, range capture, and tuner policies use named configurations over one capture and estimator core.
Rejection remains observable. Quiet, unclear, out-of-band, stale, and discontinuous results remain typed local events instead of becoming indistinguishable null.
Fallback stays available. An analyser-based source and no-microphone play preserve browser and offline resilience.
Audio stays private. Diagnostics aggregate local metrics. Raw PCM is neither transmitted nor persisted by default.

Proposed contract shape

type PitchObservation =
  | {
      kind: 'voiced'
      sequence: number
      capturedAtAudioTime: number   // midpoint of the analysed PCM window
      emittedAtPerformanceTime: number
      windowSamples: number
      raw: { hz: number; midi: number; clarity: number; rms: number }
      filtered: { hz: number; midi: number }
    }
  | {
      kind: 'unvoiced'
      sequence: number
      capturedAtAudioTime: number
      rms: number
      reason: 'quiet' | 'unclear' | 'out-of-band' | 'discontinuity'
    }

interface PitchEstimator {
  estimate(samples: Float32Array, sampleRate: number): RawPitchEstimate
}

interface PcmFrameSource {
  start(signal: AbortSignal): AsyncIterable<PcmWindow>
  stop(): Promise<void>
}
Worklet decision boundary. A fixed-hop capture adapter is the target. An AudioWorkletProcessor should capture and timestamp PCM only if the device benchmark supports it. CPU-heavy McLeod estimation should run outside the audio render callback, typically in a worker, so detector cost cannot interrupt output audio.

07 · Sequence

Phased delivery plan

Each phase ends with evidence that unlocks the next. Threshold and DSP work starts after a reproducible baseline exists.

Phase 0 — Establish the truth set

Measurement before tuning
  • Extract a pure PitchEstimator adapter around the current pitchy call without changing shipped behavior.
  • Create deterministic PCM generators for sine sweeps, vibrato, glides, harmonics, amplitude ramps, clipping, dropouts, pink noise, rumble, and competing tones.
  • Add legally usable vocal fixtures with annotated steady regions. Raw recordings of children shall not enter the repository without approved consent and retention controls.
  • Build a metrics runner for cents error, octave-error rate, voiced precision/recall, onset and release delay, observation gaps, and estimator CPU cost.
  • Run speaker playback-only controls at multiple volumes, device distances, and headphone states. Record actual track constraints and room notes.
  • Confirm the supported browser and device matrix. The current specification is <TO SUPPLY>.
Exit gate: The baseline report is reproducible in CI, the physical bleed experiment is recorded, and product owners approve measurable quality thresholds.

Phase 1 — Fix boundaries and lifecycle

Behavior-preserving refactor
  • Move shared context creation to audio/context.ts and equal-temperament conversion to audio/pitch-units.ts.
  • Split browser acquisition into MicrophoneSession with explicit states, cancellation, idempotent stop, typed failures, and partial-start cleanup.
  • Add sequence and audio timestamps to observations. Separate raw and filtered pitch fields.
  • Represent rejections with reasons for diagnostics while preserving a simple latest-voiced view for screens.
  • Expire median state by elapsed time and reset it across silence or discontinuity. Add regression tests for old-note carryover and field coherence.
  • Introduce named gameplay, rangeCapture, and tuner policies with current constants as the initial values.
Exit gate: Existing clean-tone behavior remains within the Phase 0 baseline, concurrent lifecycle tests leave zero active tracks, and current UI flows retain no-microphone fallback behavior.

Phase 2 — Make time deterministic

Decouple audio from rendering
  • Implement fixed-hop PcmFrameSource prototypes. Compare analyser polling, worklet-to-worker capture, and browser fallback on the supported matrix.
  • Publish each unique observation to logic once. Let rAF read only the latest state for avatar and tuner rendering.
  • Replace StablePitchCapture.windowFrames and silentFrames with hold and dropout durations measured in audio time.
  • Replace gameplay frame tallies with an interval-based contour or duration-weighted accumulator. Track observed, voiced, matched, and unavailable durations separately.
  • Map each observation’s capture timestamp to the song transport before applying device calibration. Preserve octave folding and current child-friendly score semantics until shadow comparisons are approved.
  • Handle source gaps explicitly so a render or worker stall does not become a silent score penalty.
Exit gate: One recorded observation stream produces the same range lock and note outcomes when the UI is simulated at 30, 60, and 120 Hz. Device CPU and output-audio glitch budgets pass approved thresholds.

Phase 3 — Adapt to device and room

Data-driven signal policy
  • Compare unprocessed input with browser echo cancellation enabled during gameplay. Select by false-score and vocal-accuracy results, not by assumption.
  • Measure guide-volume changes, cue-only playback, speaker placement, and headphone guidance before implementing reference cancellation.
  • If residual guide leakage remains material, prototype known-reference suppression behind the pipeline interface. Full adaptive cancellation should require a separate DSP design and benchmark.
  • Estimate local noise floor during explicit quiet windows. Tune adaptive level gating and hysteresis against the fixture and device corpus.
  • Tune frequency bounds, clarity use, smoothing, and onset behavior per consumer policy. Preserve current values when evidence does not support a change.
  • Move microphone latency from singer state into device-local audio settings. Store measured calibration separately from detector processing delay.
Exit gate: Playback-only sessions cannot land notes on the supported speaker matrix, vocal fixtures meet approved accuracy gates, and quiet/noisy conditions produce distinguishable local diagnostics.

Phase 4 — Diagnose, roll out, and align documentation

Operational confidence
  • Extend #/tuner with raw versus filtered pitch, rejection reason, noise floor, actual track settings, analysis cadence, observation age, and device calibration.
  • Add a local diagnostic export containing aggregate metrics and configuration only. The export shall exclude raw PCM and identity data.
  • Run old and new pipelines in local shadow mode against the same PCM during development. Compare observations and note outcomes before switching the active policy.
  • Roll out through a local feature flag with an immediate fallback to the baseline implementation.
  • Revise L2 requirements from fixed implementation constants to approved quality outcomes where appropriate.
  • Update detailed design diagrams and add an ADR for capture cadence, estimator placement, signal policy, and acoustic leakage handling.
Exit gate: The selected pipeline passes the full unit, signal, lifecycle, browser, physical-device, privacy, and fallback gates. Requirements and detailed designs describe the shipped architecture.
Changes outside the first slice. A new detector algorithm, aggressive threshold reduction, clarity-weighted scoring, graded cents scoring, attack discounts, and adaptive echo cancellation all change product behavior. Each should enter through the Phase 0 corpus and a separately approved scoring or DSP change.

10 · Decision log

Open decisions

These choices affect architecture or product behavior. Phase 0 supplies the evidence for each decision.

Decide after benchmark

PCM capture implementation

Compare current analyser polling with an AudioWorklet capture adapter and worker estimation. The selected implementation should meet cadence, CPU, output-audio, and browser-fallback gates.

Decide after bleed test

Speaker leakage strategy

Compare browser echo cancellation, guide mix changes, cue-only output, headphone guidance, and known-reference processing. The smallest strategy that passes the playback-only gate should ship first.

Decide with product

Supported device matrix

Browser and device support is not stated as a verifiable requirement. The matrix should name the minimum browser, operating system, and representative low-end device used for quality and performance gates.

Decide with privacy review

Human vocal fixtures

The corpus should use licensed or consented recordings with defined provenance, retention, and access. Synthetic audio alone cannot qualify human singing, while child audio requires added safeguards.

Separate product change

Scoring semantics

Time-based evidence removes display dependence without requiring graded cents credit, attack discounts, or clarity weighting. Those changes should receive separate acceptance criteria and child-experience validation.

Decide after timing baseline

Calibration experience

The architecture should separate output, capture, analysis, and manual calibration terms. An automatic sound check may replace the zero default only after device measurements establish a safe method.
