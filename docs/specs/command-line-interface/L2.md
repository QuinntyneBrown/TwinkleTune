# Command-Line Interface — L2 Detailed Requirements

**Subsystem code:** CL
**Specification level:** L2 (detailed / verifiable)
**Baseline:** v1.10 · **Status:** Approved
**Traces up to:** [L1.md](./L1.md)

---

## 1. Purpose & reading guide

Verifiable requirements for `TwinkleTune.Cli`, the family server's operations tool. The subsystem is
specified ahead of implementation; the intended realisation is a new `backend/src/TwinkleTune.Cli`
project (packaged as a .NET tool) that reuses `backend/src/TwinkleTune.Application/DependencyInjection.cs`
(`AddApplicationServices`), `backend/src/TwinkleTune.Infrastructure/DependencyInjection.cs`
(`AddInfrastructure`), the seed catalogue currently in
`backend/src/TwinkleTune.Infrastructure/Persistence/SeedData.cs`, and `AppDbContext`. Where a
requirement names a command, option, exit code, or package/command name, that value is the
acceptance value for the v1.10 baseline; changing it is a change to the requirement. This subsystem
supersedes the *implicit start‑up seeding* of FS‑L2‑4 with the *explicit `seed` command* of
CL‑L2‑4 / CL‑L2‑5.

Requirement keywords **SHALL / SHOULD / MAY** carry their RFC 2119 meaning (see the master
[README](../README.md) §1.1).

## 2. Detailed requirements

### CL-L2-1 — Installable .NET tool package
- **Traces to:** CL-L1-1 · **Priority:** Should
- **Source:** `TwinkleTune.Cli.csproj` (`PackAsTool=true`, `PackageId=TwinkleTune.Cli`, `ToolCommandName=twinkletune`); ADR‑0003
- **Requirement:** The CLI project shall be packable as a .NET tool (`PackAsTool=true`) producing a
  NuGet package installable with `dotnet tool install` as either a global tool or a
  tool‑manifest‑local tool.

**Acceptance criteria**
> **GIVEN** the built package
> **WHEN** `dotnet tool install` targets it (global or local)
> **THEN** the tool installs and exposes an executable command without error.

> **GIVEN** an installed tool
> **WHEN** `dotnet tool uninstall` is run for it
> **THEN** the command is removed cleanly.

---

### CL-L2-2 — Stable command name and metadata
- **Traces to:** CL-L1-1 · **Priority:** Should
- **Source:** `ToolCommandName`; assembly/package version metadata
- **Requirement:** The installed tool shall be invocable by a stable command name (`twinkletune`),
  and shall report its version via `--version`.

**Acceptance criteria**
> **GIVEN** the installed tool
> **WHEN** `twinkletune --version` is run
> **THEN** it prints the tool's version and exits with code 0.

> **GIVEN** the tool baseline
> **WHEN** the command name is inspected across releases
> **THEN** it is unchanged (renaming the command is a breaking change to this requirement).

---

### CL-L2-3 — Root command and discoverable command tree
- **Traces to:** CL-L1-1, CL-L1-3 · **Priority:** Should
- **Source:** System.CommandLine `RootCommand` + sub‑commands; auto‑generated help
- **Requirement:** The CLI shall present a System.CommandLine root command whose sub‑commands are
  discoverable via `--help`, list a one‑line description each, and whose invocation with no command
  shows help rather than performing an action.

**Acceptance criteria**
> **GIVEN** the tool
> **WHEN** `twinkletune --help` (or `twinkletune` with no arguments) is run
> **THEN** the available commands, each with a short description, and global options are listed.

> **GIVEN** the tool
> **WHEN** an unknown command or option is supplied
> **THEN** it prints a parse error to standard error and exits with a non‑zero code.

---

### CL-L2-4 — `seed` command (idempotent)
- **Traces to:** CL-L1-2 · **Priority:** Must
- **Source:** new `Commands/SeedCommand.cs`; reuses the seed catalogue from `SeedData.cs`
- **Requirement:** The CLI shall provide a `seed` command that ensures the schema exists and writes
  the eight default avatars and the seven public‑domain seed songs **only when they are absent**, so
  the operation is idempotent.

**Acceptance criteria**
> **GIVEN** an empty (or non‑existent) data store
> **WHEN** `twinkletune seed` is run
> **THEN** the schema is created, the eight avatars and seven songs are written, and the command exits 0
> reporting what it created.

> **GIVEN** an already‑seeded store
> **WHEN** `twinkletune seed` is run again
> **THEN** no duplicate avatars or songs are created and the command exits 0 reporting that seeding
> was already satisfied.

---

### CL-L2-5 — Seeding moved out of server startup
- **Traces to:** CL-L1-2 · **Priority:** Must · **Supersedes:** FS‑L2‑4 (start‑up seeding)
- **Source:** `Api/Program.cs` (the `SeedData.EnsureSeededAsync` call at startup is removed); README/run docs point operators at `twinkletune seed`
- **Requirement:** Seeding shall no longer occur as an implicit side effect of server startup; the
  `seed` command shall be the product's seeding mechanism, and the run documentation shall instruct
  operators to run it as an explicit provisioning step. The server shall still ensure its schema
  exists on startup but shall not write seed rows.

**Acceptance criteria**
> **GIVEN** an unseeded data store
> **WHEN** the API host starts
> **THEN** it does not silently write seed avatars or songs (it may create the empty schema).

> **GIVEN** the same unseeded store
> **WHEN** `twinkletune seed` is subsequently run
> **THEN** the store is populated, and the API then serves the seeded avatars and songs.

---

### CL-L2-6 — Single canonical seed definition, shared with the server
- **Traces to:** CL-L1-2 · **Priority:** Should
- **Source:** the seed catalogue extracted to a shared location referenced by both `Cli` and `Infrastructure`
- **Requirement:** The eight avatars and seven seed songs shall be defined once, in a single canonical
  location shared by the CLI and the backend, so the two never disagree about the seed content.

**Acceptance criteria**
> **GIVEN** the seed catalogue
> **WHEN** the CLI seeds a store and the server reads it
> **THEN** the avatars and songs the server serves are exactly those the CLI wrote, with no second,
> divergent seed list existing in the codebase.

---

### CL-L2-7 — Argument/option parsing and validation
- **Traces to:** CL-L1-3 · **Priority:** Should
- **Source:** System.CommandLine options with parsers/validators; e.g. a `--data-path` / `--connection` override
- **Requirement:** Command options shall be parsed and validated by System.CommandLine, with invalid
  values reported as a parse error before any handler runs.

**Acceptance criteria**
> **GIVEN** a command that accepts an option (e.g. a data‑store override)
> **WHEN** it is supplied a malformed value
> **THEN** a validation error is printed and the command exits non‑zero without executing its effect.

> **GIVEN** a valid option value
> **WHEN** the command runs
> **THEN** the parsed value is bound and used by the handler.

---

### CL-L2-8 — Composition with the Generic Host and shared DI
- **Traces to:** CL-L1-4 · **Priority:** Should
- **Source:** `Program.cs` builds `Host.CreateApplicationBuilder(...)`; registers `AddApplicationServices()` + `AddInfrastructure(connectionString, photosPath)`
- **Requirement:** The CLI shall compose its services through a Microsoft.Extensions Generic Host that
  registers the backend's `AddApplicationServices()` and `AddInfrastructure(...)`, so command handlers
  resolve the same services and repositories the server uses.

**Acceptance criteria**
> **GIVEN** the CLI host
> **WHEN** it is built
> **THEN** the service provider resolves the shared Application services and Infrastructure
> repositories/`AppDbContext`, using the same registrations as the Api.

> **GIVEN** a command handler
> **WHEN** it needs data logic
> **THEN** it obtains it from the shared services via DI rather than re‑implementing it.

---

### CL-L2-9 — Configuration with server‑matching keys and precedence
- **Traces to:** CL-L1-4, CL-L1-7 · **Priority:** Should
- **Source:** `Microsoft.Extensions.Configuration` (env vars, optional `appsettings.json`, command options); keys `DataPath`, `ConnectionStrings:Default`, `PhotosPath`
- **Requirement:** The CLI shall resolve its data‑store location from the same configuration keys as
  the server (`DataPath`, `ConnectionStrings:Default`, `PhotosPath`), with a clear precedence of
  command option → environment/`appsettings` → default, defaulting to the same data directory and
  `twinkletune.db` the server uses.

**Acceptance criteria**
> **GIVEN** no configuration and no option
> **WHEN** a command runs
> **THEN** it targets the same default data directory and `twinkletune.db` the server defaults to.

> **GIVEN** a connection string / data path supplied by environment or `appsettings`, and a different
> one supplied as a command option
> **WHEN** a command runs
> **THEN** the command option wins, then environment/file, then the default.

---

### CL-L2-10 — Structured logging with configurable verbosity
- **Traces to:** CL-L1-4, CL-L1-8 · **Priority:** Should
- **Source:** `Microsoft.Extensions.Logging` console provider; a global `--verbosity` option
- **Requirement:** The CLI shall log through `Microsoft.Extensions.Logging` to the console, with a
  global verbosity option controlling the minimum level, so routine runs are quiet and diagnostics
  are available on demand.

**Acceptance criteria**
> **GIVEN** the default verbosity
> **WHEN** a command runs successfully
> **THEN** it emits concise informational output and no debug noise.

> **GIVEN** a raised verbosity (e.g. `--verbosity debug`)
> **WHEN** the same command runs
> **THEN** additional diagnostic log entries are emitted.

---

### CL-L2-11 — Command‑per‑file, single‑responsibility handlers
- **Traces to:** CL-L1-5, CL-L1-6 · **Priority:** Should
- **Source:** `Commands/` folder — one command per file/class implementing a common command contract; handlers depend on injected abstractions
- **Requirement:** Each command shall live in its own file and class implementing a common command
  contract, shall have a single responsibility, and shall depend only on injected service/repository
  abstractions — containing orchestration, not embedded data‑access or a shared god‑file `switch`.

**Acceptance criteria**
> **GIVEN** the CLI source
> **WHEN** the `Commands/` folder is inspected
> **THEN** there is a one‑to‑one mapping of command to file/class, and no single file enumerates or
> dispatches all commands via a hand‑written switch.

> **GIVEN** any command class
> **WHEN** its constructor is inspected
> **THEN** it depends on abstractions (services/repositories) supplied by DI, not on concrete data
> access it constructs itself.

---

### CL-L2-12 — Open/closed command registration
- **Traces to:** CL-L1-5, CL-L1-6 · **Priority:** Should
- **Source:** each command registered in DI and assembled into the `RootCommand` by a composition root
- **Requirement:** Commands shall be registered uniformly (in DI) and assembled into the root command
  by a composition root, so a new command is added by creating its file and registering it — without
  editing existing command classes.

**Acceptance criteria**
> **GIVEN** the desire to add a new command
> **WHEN** a new command file/class is created and registered
> **THEN** it appears in the command tree and help with no modification to any existing command class.

---

### CL-L2-13 — Standard, deterministic exit codes
- **Traces to:** CL-L1-3, CL-L1-8 · **Priority:** Should
- **Source:** handler return / `Environment.ExitCode`; documented codes (0 success, non‑zero failure/validation)
- **Requirement:** Every command shall return a deterministic process exit code — 0 on success and a
  documented non‑zero code on validation error or failure — so scripts and CI can branch on the
  result.

**Acceptance criteria**
> **GIVEN** a command that completes successfully
> **WHEN** the process exits
> **THEN** the exit code is 0.

> **GIVEN** a command that fails validation or execution
> **WHEN** the process exits
> **THEN** the exit code is a documented non‑zero value and an error message is written to standard
> error.

---

### CL-L2-14 — Shared single data store; no second source of truth
- **Traces to:** CL-L1-7 · **Priority:** Must · **See also:** FS‑L2‑3, FS‑L2‑19
- **Source:** `AddInfrastructure(connectionString, photosPath)` bound to the same SQLite file + photos folder as the server
- **Requirement:** The CLI shall operate on the same single SQLite database file and photos folder as
  the server, ensuring the schema exists before a write, and shall not introduce a separate or
  divergent store.

**Acceptance criteria**
> **GIVEN** the server's configured data directory
> **WHEN** the CLI runs a write command against the default/target configuration
> **THEN** it reads and writes the same `.db` file (and photos folder) the server uses, creating the
> schema first if absent.

---

### CL-L2-15 — Off the child‑runtime path (offline‑first preserved)
- **Traces to:** CL-L1-7 · **Priority:** Must · **See also:** FS‑L2‑15
- **Source:** the CLI is a separate executable, not referenced by the frontend or the running Api request path
- **Requirement:** No CLI capability shall be required for solo play or for the running child‑facing
  app; the CLI is an out‑of‑band operator tool and is not on the request path of the server or client.

**Acceptance criteria**
> **GIVEN** the CLI is never installed or run
> **WHEN** a child plays solo and a family uses the app against a *seeded* server
> **THEN** every runtime behaviour still works; the CLI's absence at runtime changes nothing.

---

### CL-L2-16 — Local‑only, no outbound network
- **Traces to:** CL-L1-7 · **Priority:** Should · **See also:** FS‑L2‑11
- **Source:** command handlers touch only the local data store; no HTTP client to external services
- **Requirement:** The CLI shall act only on the local data store and shall make no outbound network
  calls, consistent with the LAN‑only, on‑premises posture.

**Acceptance criteria**
> **GIVEN** any command
> **WHEN** it runs
> **THEN** it accesses only the local database/photos and initiates no connection to the public
> internet.

---

### CL-L2-17 — Deterministic, injectable time
- **Traces to:** CL-L1-8 · **Priority:** Should · **See also:** FS‑L2‑17
- **Source:** shared `TimeProvider` registration from `AddApplicationServices()`; seed timestamps derive from it
- **Requirement:** Time‑dependent behaviour in command handlers (e.g. seed `UpdatedAt` timestamps)
  shall use the injectable `TimeProvider` so it is deterministic under test.

**Acceptance criteria**
> **GIVEN** a test that substitutes the time provider
> **WHEN** a command that stamps time runs
> **THEN** the written timestamps reflect the substituted clock.

---

### CL-L2-18 — Unit‑testable handlers without process launch
- **Traces to:** CL-L1-8 · **Priority:** Should · **See also:** FS‑L2‑18
- **Source:** handlers are classes resolved from DI; a test host composes the same services over an in‑memory/temp SQLite store
- **Requirement:** Command handlers shall be invokable directly against a composed service provider
  (e.g. a temp‑file SQLite store) so their behaviour is unit/integration‑testable without launching
  the installed process.

**Acceptance criteria**
> **GIVEN** a test that composes the CLI's services over a temp SQLite store
> **WHEN** it invokes the seed handler directly and then re‑invokes it
> **THEN** the first run seeds the store and the second is a no‑op, asserted without spawning the tool
> process.
