# Command-Line Interface — L1 High-Level Requirements

**Subsystem code:** CL
**Specification level:** L1 (capability / high‑level)
**Baseline:** v1.10 · **Status:** Approved
**Detailed requirements:** [L2.md](./L2.md)
**Primary dependencies:** consumes Family Server Platform (FS) — the Application/Infrastructure layers, the SQLite data store, and the seed catalogue; operationally serves the grown‑up/operator, not the child runtime
**Governing decisions:** ADR‑0002 (Clean Architecture, EF Core + SQLite, no‑auth LAN), ADR‑0003 (CLI tooling and explicit seeding)

---

## 1. Purpose

`TwinkleTune.Cli` is the family server's operations tool — a small, first‑party command‑line
application a grown‑up installs and runs to administer the server's data store out‑of‑band from the
running web host. Its founding responsibility is **seeding**: the default avatars and the seven
public‑domain songs are written by an explicit `seed` command instead of implicitly at server
startup, so an operator decides deterministically when seed data is created and can re‑run it safely.

The tool is built on **System.CommandLine** for its command tree, help, and parsing; it is composed
with **Microsoft.Extensions** (Generic Host, Dependency Injection, Configuration, Logging) so it
resolves and reuses the *same* Application/Infrastructure services the server does — no second,
drifting copy of the data logic. It is packaged and distributed as an **installable .NET tool**, and
its source is organised with a **command‑per‑file pattern** — one command, one file, one class — so
the command surface is discoverable and grows by addition rather than modification. The design is
held to **SOLID**: each command is a single‑responsibility unit that depends on injected abstractions,
and new commands extend the tool without editing the ones already there.

## 2. Scope

### In scope

- The tool itself: a `TwinkleTune.Cli` executable project packaged as an installable global/local
  .NET tool with a stable command name.
- The **command tree** built on System.CommandLine: a root command, sub‑commands, help, `--version`,
  argument/option parsing and validation, and standard process exit codes.
- **Seeding as a command**: the `seed` command that idempotently writes the default avatars and the
  seven seed songs, replacing implicit start‑up seeding as the product's seeding mechanism.
- **Composition with Microsoft.Extensions**: Generic Host / DI wiring that registers the backend's
  `AddApplicationServices()` and `AddInfrastructure(...)` so command handlers depend on the shared
  services, plus Configuration (same keys as the server) and Logging.
- The **command‑per‑file / SOLID** organisation: a uniform command contract, DI registration of each
  command, and a composition root that assembles the root command from the registered commands.
- **Data‑store targeting and safety**: operating on the same single SQLite file (+ photos folder),
  ensuring the schema exists before writing, idempotency, deterministic exit codes, and structured
  logging.

### Out of scope

- The **domain semantics** of avatars and songs and the actual seed content — **SL** (Song Library)
  and **FS** own the entities and the catalogue; CL only invokes the shared seed logic.
- The **server's HTTP/SignalR surface** — **FS**; the CLI is not a client of the API and does not
  start the web host.
- The **child‑facing runtime** — no CL capability is on the path of solo play or the family app;
  CL is an operator tool (see CL‑L1‑7).

## 3. Context & dependencies

The CLI is a fifth composition root over the existing four backend projects. Where `Api/Program.cs`
builds a `WebApplication` and maps controllers and hubs, `Cli` builds a Generic **Host**, registers
the identical `AddApplicationServices()` + `AddInfrastructure(connectionString, photosPath)`, and
dispatches a System.CommandLine command tree instead of serving HTTP. It reads the same
configuration keys the server does (`DataPath`, `ConnectionStrings:Default`, `PhotosPath`) so it
addresses the same `.db` file and photos folder, and it reuses the one canonical seed definition so
the CLI and the server never disagree about what "seeded" means. The tool is installed with
`dotnet tool install` and invoked by its command name; it exits with a conventional status code and
writes structured logs, so it is equally usable by a grown‑up at a prompt and by a deployment script.

## 4. High-level requirements

| ID | Requirement | Priority | Rationale |
|----|-------------|----------|-----------|
| **CL-L1-1** | The product shall provide a first‑party command‑line tool, `TwinkleTune.Cli`, for operational tasks against the family server's data store, packaged and distributed as an installable .NET tool with a stable command name. | Should | A grown‑up needs a supported way to administer the server's data without editing code or hand‑running SQL; a packaged tool is `dotnet tool install`‑and‑go (ADR‑0003). |
| **CL-L1-2** | Data seeding shall be performed by an explicit CLI command rather than implicitly at server startup, and shall be idempotent, so operators deterministically control when seed data is written and repeated runs never duplicate it. | Must | Moves a hidden start‑up side effect into a deliberate, observable, re‑runnable operation; the founding purpose of the tool (ADR‑0003). Supersedes FS‑L2‑4's start‑up seeding. |
| **CL-L1-3** | The CLI shall be built on System.CommandLine, presenting a discoverable command tree with help, `--version`, argument/option parsing and validation, and standard process exit codes. | Should | A conventional, self‑documenting command surface that behaves like the .NET tools operators already know; parsing/validation/help come from the framework rather than hand‑rolled. |
| **CL-L1-4** | The CLI shall be composed with Microsoft.Extensions (Generic Host, Dependency Injection, Configuration, Logging), reusing the backend's Application/Infrastructure service registrations so its behaviour matches the server's. | Should | One set of services, one behaviour: the CLI must not fork the data logic. Host/DI/Config/Logging give it the same composition model as the Api (P‑consistency; matches the maintainer's stack). |
| **CL-L1-5** | The CLI shall follow SOLID design: each command is a single‑responsibility unit that depends on injected abstractions, and the command surface is open to extension (adding a command) without modification of existing commands. | Should | Keeps handlers thin and testable, keeps data access behind service/repository interfaces, and lets the tool grow safely — an explicit request for the tool's internal design. |
| **CL-L1-6** | The CLI source shall adopt a command‑per‑file pattern — one command per file and class, registered uniformly — so the command surface is discoverable and extended by addition. | Should | A predictable file‑to‑command mapping makes the tool easy to read, review, and extend; no god‑file `switch` accreting every operation. |
| **CL-L1-7** | The CLI shall respect the server's configuration and data‑ownership model — operating on the same single SQLite file and photos folder via the same configuration keys — and shall remain off the path of solo play and the running child‑facing app. | Must | The CLI is an operator tool that shares the server's one durable state (FS‑L1‑2, FS‑L1‑6); it must not become a second source of truth, and offline‑first solo play (P2) must never depend on it. |
| **CL-L1-8** | The CLI shall be testable and observable — deterministic exit codes, structured logging, injectable time, and command handlers unit‑testable without launching the process. | Should | Consistent with FS‑L1‑7; an ops tool that scripts and CI invoke must fail loudly and predictably and must be coverable by tests. |

## 5. Assumptions & constraints

- Target framework `net10.0` (fall back to the installed LTS if unavailable), consistent with FS.
- Packaged with `PackAsTool=true`; installable as a global or tool‑manifest‑local .NET tool. The tool
  is distributed to grown‑ups/operators, not shipped inside the child app.
- Configuration keys mirror the server: `DataPath`, `ConnectionStrings:Default`, `PhotosPath`; the
  CLI defaults to the same data directory and `twinkletune.db` the server uses when unconfigured, and
  a command option may override the target for a single invocation.
- Schema is created with `EnsureCreated()` (as in FS) before a write command runs against an empty
  store; migrations are introduced only when the schema must evolve.
- The seed catalogue is the single canonical definition of the eight avatars and seven public‑domain
  songs, shared by the CLI and the server rather than duplicated.
- The CLI is LAN/host‑local and touches only the local data store; it makes no outbound network calls
  and is not exposed to the internet (P4).
