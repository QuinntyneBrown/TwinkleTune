# Family Server Platform — L1 High-Level Requirements

**Subsystem code:** FS
**Specification level:** L1 (capability / high‑level)
**Baseline:** v1.0 · **Status:** Approved
**Detailed requirements:** [L2.md](./L2.md)
**Primary dependencies:** consumed by Player Profiles (PP), Song Library (SL), Family High Scores (HS), Duet Multiplayer (DM)
**Governing decisions:** ADR‑0001 (family‑scoped backend), ADR‑0002 (Clean Architecture, EF Core + SQLite, no‑auth LAN)

---

## 1. Purpose

The Family Server Platform is the optional, self‑hosted backend that turns TwinkleTune from a solo app
into a family one — profiles, songs, photos, high scores, and duets — while keeping the whole thing tiny,
private, and on the family's own hardware. It is built as **Clean Architecture** over **EF Core +
SQLite**, deployed **LAN‑only with no authentication by design**, and paired with a client that treats
the server as a progressive enhancement it can always do without. The platform's job is to host the
feature subsystems' data and realtime surface, safely and simply, and to degrade gracefully to solo
play whenever it is absent.

## 2. Scope

### In scope

- The layered architecture (Domain, Application, Infrastructure, Api) and its dependency rules.
- Zero‑ops persistence: SQLite single file, a photos folder, JSON‑column song storage, schema creation,
  and idempotent seeding.
- The hosting composition: REST controllers, the SignalR hub, CORS, OpenAPI (dev), and a health probe.
- The security posture: no authentication, CORS‑restricted, LAN‑only, and the documented "not for the
  internet" boundary.
- The client's server feature‑detection and the whole‑product graceful‑degradation contract.
- The data‑ownership model (device vs server) and minimal on‑premises data.
- Testability: deterministic time and integration/unit test seams.

### Out of scope

- The domain semantics of each entity — **SL / PP / HS / DM** (FS hosts them).
- The client screens and their offline behaviours — the respective feature subsystems (FS defines the
  *contract* they degrade against).

## 3. Context & dependencies

The server composes four projects with dependencies pointing inward only: a dependency‑free Domain,
an Application layer of plain services over repository interfaces, an Infrastructure layer of EF Core +
SQLite and disk photo storage, and a minimal‑hosting Api layer exposing controllers, a SignalR duet hub,
CORS, and health. The whole backend state is one `.db` file plus a photos folder. The client resolves a
base URL, probes `/health` to feature‑detect, and every server‑backed feature has a solo or cached
fallback.

## 4. High-level requirements

| ID | Requirement | Priority | Rationale |
|----|-------------|----------|-----------|
| **FS-L1-1** | The backend shall follow Clean Architecture with four layers and inward‑only dependencies, keeping the Domain dependency‑free and the core independently testable. | Should | Matches the maintainer's stack (ADR‑0002); a pure core is testable without hosting. |
| **FS-L1-2** | The backend shall persist all durable state as a single SQLite file plus a photos folder, using a JSON column for song content, creating its schema and seeding idempotently. | Must | Zero‑ops, file‑backupable persistence appropriate to family scale; JSON column mirrors the client shape. |
| **FS-L1-3** | The backend shall expose a minimal REST + SignalR surface with CORS and a health endpoint, and developer API docs in development only. | Must | The concrete integration surface the client and duets depend on; health enables feature detection. |
| **FS-L1-4** | The backend shall run without authentication, restricted by CORS to configured origins, intended for home‑LAN use only, and shall document that it must not be exposed to the internet. | Must | Deliberate no‑auth LAN scope (ADR‑0002); honesty about the boundary is a safety requirement. |
| **FS-L1-5** | The client shall feature‑detect server availability and guarantee that solo play never requires the API, with every server‑backed feature degrading gracefully. | Must | Offline‑first (P2) is a product‑wide promise the platform must uphold. |
| **FS-L1-6** | The platform shall implement a clear data‑ownership split — on‑device rewards, server‑owned profiles/songs/photos/high‑scores, person‑vs‑device properties — minimising on‑premises children's data. | Must | Data minimisation and clarity of where each datum lives (P3). |
| **FS-L1-7** | The backend shall be built for testability, using injectable time and integration/unit test seams. | Should | Deterministic, host‑level tests (including the 2‑client duet flow) protect the platform. |

## 5. Assumptions & constraints

- Target framework `net10.0` (fall back to the installed LTS if unavailable).
- Default client base URL `http://localhost:5240`; default server CORS origins include the Vite dev/preview ports.
- Schema is created with `EnsureCreated()` + idempotent seeding for v1; migrations are introduced only when the schema must evolve.
- Duet rooms are in‑memory and non‑persistent (DM); the durable state is the `.db` file and photos folder.
