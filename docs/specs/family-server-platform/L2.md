## 1. Purpose & reading guide

Verifiable requirements for the backend platform and the client's degradation contract. Sources:
`backend/src/TwinkleTune.Api/Program.cs`, the four project `DependencyInjection.cs` files,
`backend/src/TwinkleTune.Infrastructure/Persistence/AppDbContext.cs` and `SeedData.cs`,

`backend/src/TwinkleTune.Api/appsettings.json`, `frontend/src/api/client.ts`,
ADR‑0001 and ADR‑0002.

## 2. Detailed requirements

### FS-L2-1 — Layered architecture with inward dependencies
- **Traces to:** FS-L1-1 · **Priority:** Should
- **Source:** project structure (`Domain`, `Application`, `Infrastructure`, `Api`); Domain has no project references
- **Requirement:** The backend shall be split into Domain, Application, Infrastructure, and Api
  projects, with dependencies pointing inward only and the Domain depending on nothing.

**Acceptance criteria**
> **GIVEN** the solution's project references
> **WHEN** they are inspected
> **THEN** Domain references no other project, and Api/Infrastructure/Application never form an outward or cyclic dependency.

---

### FS-L2-2 — Plain services over repository interfaces
- **Traces to:** FS-L1-1 · **Priority:** Should
- **Source:** `Application` (services + `Abstractions/IRepositories.cs`; no MediatR)
- **Requirement:** The Application layer shall implement business logic as plain services over
  repository interfaces, without a CQRS/mediator framework.

**Acceptance criteria**
> **GIVEN** the Application layer
> **WHEN** its dependencies are inspected
> **THEN** services depend on repository interfaces and carry no MediatR/CQRS dependency.

---

### FS-L2-3 — SQLite persistence with configurable paths
- **Traces to:** FS-L1-2 · **Priority:** Must
- **Source:** `Program.cs` (data dir; connection string; photos path); `Infrastructure/DependencyInjection.cs` (`UseSqlite`)
- **Requirement:** The backend shall persist to a SQLite database and a photos folder whose locations
  default under a data directory but are overridable by configuration.

**Acceptance criteria**
> **GIVEN** default configuration
> **WHEN** the server starts
> **THEN** it creates the data directory and uses a SQLite database file and a photos subfolder within it.

> **GIVEN** an overriding connection string / photos path in configuration
> **THEN** those locations are used instead.

---

### FS-L2-4 — Schema creation and idempotent seeding
- **Traces to:** FS-L1-2 · **Priority:** Must
- **Source:** `Program.cs` (`EnsureCreated`; `SeedData.EnsureSeededAsync`); `SeedData.cs` (avatars and seven songs seeded only if absent)
- **Requirement:** On startup the backend shall ensure the schema exists and seed the default avatars
  and the seven public‑domain songs only when they are absent, so repeated startups do not duplicate seed
  data.

**Acceptance criteria**
> **GIVEN** an empty database
> **WHEN** the server starts
> **THEN** the schema is created and the eight avatars and seven songs are seeded.

> **GIVEN** an already‑seeded database
> **WHEN** the server restarts
> **THEN** no duplicate avatars or songs are created.

---

### FS-L2-5 — JSON‑column song storage
- **Traces to:** FS-L1-2 · **Priority:** Should
- **Source:** `AppDbContext.cs` (Phrases via JSON value converter + value comparer)
- **Requirement:** Song phrases/notes shall persist as a single JSON document via a value converter,
  with a value comparer so EF change tracking behaves correctly.

**Acceptance criteria**
> **GIVEN** a song with phrases
> **WHEN** it is saved and reloaded
> **THEN** its phrases round‑trip exactly through the JSON column, and unchanged phrases are not spuriously marked modified.

---

### FS-L2-6 — Repository query behaviour
- **Traces to:** FS-L1-2 · **Priority:** Should
- **Source:** `Repositories.cs` (`AsNoTracking` reads; ordering; SQLite `DateTimeOffset` sorted in memory)
- **Requirement:** Read queries shall be no‑tracking, lists shall be ordered as their consumers require,
  and ordering by a `DateTimeOffset` (unsupported by SQLite in SQL) shall be performed in memory.

**Acceptance criteria**
> **GIVEN** singers created over time
> **WHEN** the singer list is fetched
> **THEN** it is ordered by creation time (sorted in memory) without a database error.

---

### FS-L2-7 — Dependency‑injection lifetimes
- **Traces to:** FS-L1-1 · **Priority:** Should
- **Source:** `Application/DependencyInjection.cs` (`TimeProvider.System` and `RoomService` as singletons; services scoped); `Infrastructure/DependencyInjection.cs` (repos scoped; `PhotoStorage` singleton)
- **Requirement:** Services and repositories shall be scoped; the time provider, the in‑memory room
  service, and the photo storage shall be singletons.

**Acceptance criteria**
> **GIVEN** the DI configuration
> **WHEN** it is composed
> **THEN** the room service and time provider are singletons (room state persists across requests) and per‑request services/repositories are scoped.

---

### FS-L2-8 — Hosting composition
- **Traces to:** FS-L1-3 · **Priority:** Must
- **Source:** `Program.cs` (`AddControllers`, `AddSignalR`, `MapControllers`, `MapHub<DuetHub>("/hubs/duet")`, OpenAPI mapped in development only)
- **Requirement:** The Api shall host REST controllers and the duet SignalR hub at `/hubs/duet`, and
  shall expose OpenAPI documentation in the development environment only.

**Acceptance criteria**
> **GIVEN** the running server
> **WHEN** a client connects to `/hubs/duet`
> **THEN** the duet hub accepts the connection, and REST controllers serve the API routes.

> **GIVEN** a non‑development environment
> **THEN** OpenAPI docs are not mapped.

---

### FS-L2-9 — Health endpoint
- **Traces to:** FS-L1-3 · **Priority:** Must
- **Source:** `Program.cs` (`GET /health` → 200 `{ status: "ok" }`)
- **Requirement:** The server shall expose a health endpoint returning HTTP 200 with an OK status.

**Acceptance criteria**
> **GIVEN** the running server
> **WHEN** `GET /health` is called
> **THEN** it responds 200 with a status of "ok".

---

### FS-L2-10 — CORS restriction
- **Traces to:** FS-L1-3, FS-L1-4 · **Priority:** Must
- **Source:** `Program.cs` (CORS policy "app" from `Cors:Origins`, default `http://localhost:5173`, credentials allowed); `appsettings.json`
- **Requirement:** The server shall restrict cross‑origin access to a configured list of origins
  (defaulting to the local dev/preview origins), allowing credentials, so only the intended app origins
  can call it.

**Acceptance criteria**
> **GIVEN** a configured allowed origin
> **WHEN** the app calls the API from that origin
> **THEN** the request is permitted.

> **GIVEN** an origin not in the configured list
> **THEN** the browser blocks the cross‑origin call.

---

### FS-L2-11 — No‑auth LAN‑only posture and boundary
- **Traces to:** FS-L1-4 · **Priority:** Must
- **Source:** ADR‑0002 (no authentication, LAN‑only; parent gate is the only guard); README ("home‑LAN use only — don't expose to the internet")
- **Requirement:** The server shall operate without authentication for home‑LAN use, relying on the
  client parent gate as the only guard, and the product shall document that it must not be exposed to
  the public internet (revisiting the decision before any such exposure).

**Acceptance criteria**
> **GIVEN** the shipped documentation and configuration
> **WHEN** the deployment posture is reviewed
> **THEN** it states LAN‑only, no‑auth operation and explicitly warns against internet exposure.

---

### FS-L2-12 — Safe photo storage on disk
- **Traces to:** FS-L1-4 · **Priority:** Should · **See also:** PP‑L2‑13
- **Source:** `PhotoStorage.cs` (stores under a root path; `Path.GetFileName` guards traversal; supported types only)
- **Requirement:** Photo files shall be stored under a controlled root and read back only via a
  path‑traversal‑safe lookup, accepting only supported image types.

**Acceptance criteria**
> **GIVEN** a request to read a photo by a crafted name containing path separators
> **WHEN** it is resolved
> **THEN** only the base file name within the photos root is used, preventing traversal outside it.

---

### FS-L2-13 — API client base URL and error model
- **Traces to:** FS-L1-5 · **Priority:** Must
- **Source:** `client.ts` (`API_URL` from `VITE_API_URL`, default `http://localhost:5240`; `ApiError` with messages/errors)
- **Requirement:** The client shall resolve the API base URL from configuration (defaulting to the local
  server) and shall surface server error messages and validation error lists through a typed error.

**Acceptance criteria**
> **GIVEN** no `VITE_API_URL` configured
> **THEN** the client targets `http://localhost:5240`.

> **GIVEN** a 400 response with an `errors` array
> **WHEN** a call fails
> **THEN** the client raises a typed error carrying those messages.

---

### FS-L2-14 — Server reachability probe
- **Traces to:** FS-L1-5 · **Priority:** Should
- **Source:** `client.ts` (`serverOnline`: `/health` with a 1500 ms timeout, result cached 10 s)
- **Requirement:** The client shall provide a cheap reachability probe against `/health` with a short
  timeout, caching the result briefly to avoid repeated probing.

**Acceptance criteria**
> **GIVEN** the server is reachable
> **WHEN** the probe runs
> **THEN** it returns online, and a repeat within 10 seconds returns the cached result without re‑probing.

> **GIVEN** the server is unreachable or slow beyond ~1.5 s
> **THEN** the probe returns offline.

---

### FS-L2-15 — Graceful‑degradation contract
- **Traces to:** FS-L1-5 · **Priority:** Must
- **Source:** `client.ts` header comment ("Solo play NEVER requires this"); songbook/profile/duet fallbacks across screens
- **Requirement:** Solo play shall never require the API; every server‑backed feature shall have a
  defined fallback — cached/bundled songbook, local‑only profile, duet routed to solo — so the app is
  fully usable offline.

**Acceptance criteria**
> **GIVEN** the server is entirely unavailable
> **WHEN** a child uses the app
> **THEN** she can onboard, tune her voice, browse songs, and sing with scoring — with only the family features (profiles beyond local, family scores, duets) unavailable and cleanly indicated.

---

### FS-L2-16 — Data‑ownership split
- **Traces to:** FS-L1-6 · **Priority:** Must
- **Source:** ADR‑0002 (range on Singer; latency device‑local; server owns high scores; sparkles/badges/streaks on device)
- **Requirement:** The platform shall keep on‑device the rewards (sparkles, badges, day‑streaks) and the
  mic latency (a device property); the server shall own profiles, avatars, photos, songs, and high
  scores, and the voice range shall live on the singer (a person property that follows her across
  devices).

**Acceptance criteria**
> **GIVEN** a singer used on two devices
> **WHEN** her range is captured on one
> **THEN** it is available on the other (server‑owned), while her mic latency and on‑device rewards remain per device.

---

### FS-L2-17 — Deterministic, injectable time
- **Traces to:** FS-L1-7 · **Priority:** Should
- **Source:** `Application/DependencyInjection.cs` (`TimeProvider`); services use it for timestamps; RoomService uses it for expiry
- **Requirement:** Time‑dependent logic (achievement timestamps, room start times and expiry) shall use
  an injectable time provider so it can be controlled in tests.

**Acceptance criteria**
> **GIVEN** a test that substitutes the time provider
> **WHEN** time‑dependent logic runs
> **THEN** its timestamps and expiry decisions are deterministic under the substituted clock.

---

### FS-L2-18 — Integration and unit test seams
- **Traces to:** FS-L1-7 · **Priority:** Should
- **Source:** `Program.cs` (`public partial class Program`); `tests/` (WebApplicationFactory CRUD + 2‑client SignalR duet; unit tests for validator, high‑score upsert, room service)
- **Requirement:** The Api shall expose its entry point for host‑level integration tests, and the
  platform shall be covered by unit tests (domain invariants, high‑score upsert, room service) and
  integration tests (CRUD round‑trips and a two‑client duet flow).

**Acceptance criteria**
> **GIVEN** the integration test suite
> **WHEN** it runs against the hosted app
> **THEN** CRUD endpoints round‑trip and two SignalR clients complete a create→join→start→ticks→finish→result duet flow.

---

### FS-L2-19 — Backup‑simple state footprint
- **Traces to:** FS-L1-2 · **Priority:** Could
- **Source:** ADR‑0002 ("whole backend state is two artifacts — one .db file, one photos folder")
- **Requirement:** The entire durable backend state shall be a single database file plus a photos
  folder, so backup is copying a folder.

**Acceptance criteria**
> **GIVEN** a running family server
> **WHEN** its data directory is copied
> **THEN** the copy contains the complete durable state (database file and photos) needed to restore it.
