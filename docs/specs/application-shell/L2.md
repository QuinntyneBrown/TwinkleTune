## 2. Detailed requirements

### AS-L2-1 — Hash route table and parsing
- **Traces to:** AS-L1-1 · **Priority:** Must
- **Source:** `main.ts` (`routes`; hash parsed into name + query params)
- **Requirement:** The router shall map the URL hash to one of the known screens (welcome, voice, home,
  songs, sing, results, tips, me, tuner, profiles, duet), parsing any query string into parameters
  passed to the screen.

**Acceptance criteria**
> **GIVEN** a hash of `#/sing?song=twinkle&practice=2`
> **WHEN** the router resolves it
> **THEN** the sing screen mounts with parameters `song=twinkle` and `practice=2`.

---

### AS-L2-2 — Default and unknown‑route handling
- **Traces to:** AS-L1-2 · **Priority:** Must
- **Source:** `main.ts` (empty path → home if profile else welcome; unknown name → home)
- **Requirement:** An empty route shall resolve to home when a profile exists, otherwise to onboarding;
  an unrecognised route name shall fall back to home.

**Acceptance criteria**
> **GIVEN** no profile and an empty hash
> **THEN** the welcome screen is shown.

> **GIVEN** a profile and an unknown route name
> **THEN** the home screen is shown.

---

### AS-L2-3 — Profile guard
- **Traces to:** AS-L1-2 · **Priority:** Must
- **Source:** `main.ts` (`NO_PROFILE_OK = {welcome, tuner, profiles}`; else redirect to welcome when no profile)
- **Requirement:** A screen that requires a profile shall redirect to onboarding when no profile exists;
  only welcome, tuner, and profiles shall be reachable without a profile.

**Acceptance criteria**
> **GIVEN** no profile
> **WHEN** the user navigates to `#/home`, `#/songs`, or `#/sing`
> **THEN** they are redirected to the welcome screen.

> **GIVEN** no profile
> **WHEN** the user navigates to `#/profiles` or `#/tuner`
> **THEN** the screen is shown.

---

### AS-L2-4 — Screen lifecycle
- **Traces to:** AS-L1-1 · **Priority:** Must
- **Source:** `main.ts` (previous cleanup invoked; `app.innerHTML=''`; `scrollTo(0,0)`; new screen mounted; `hashchange` listener)
- **Requirement:** On each navigation the router shall invoke the previous screen's cleanup, clear the
  mount point, reset scroll to the top, and mount the new screen; navigation shall be driven by hash
  changes and an initial route on load.

**Acceptance criteria**
> **GIVEN** an active screen with a running loop or open resource
> **WHEN** the user navigates away
> **THEN** its cleanup runs before the next screen mounts, and the page scrolls to the top.

---

### AS-L2-5 — Bottom navigation
- **Traces to:** AS-L1-3 · **Priority:** Should
- **Source:** `parts.ts` (`bottomNav`: Home, Songs, Tips, Me; active tab marked)
- **Requirement:** The primary navigation shall be a four‑item bottom bar — Home, Songs, Tips, Me — with
  the active tab visually and semantically marked.

**Acceptance criteria**
> **GIVEN** the songs screen
> **WHEN** the bottom nav renders
> **THEN** four tabs are shown and "Songs" is marked active.

---

### AS-L2-6 — Modal/dialog primitive
- **Traces to:** AS-L1-3 · **Priority:** Should
- **Source:** `modal.ts` (`showModal`: overlay + dialog role + aria‑label; backdrop click closes unless non‑dismissible)
- **Requirement:** The shell shall provide a modal primitive that renders an accessible dialog over a
  backdrop, supports a non‑dismissible mode, and closes on backdrop click when dismissible.

**Acceptance criteria**
> **GIVEN** a dismissible modal
> **WHEN** the backdrop (not the card) is clicked
> **THEN** the modal closes.

> **GIVEN** a non‑dismissible modal
> **WHEN** the backdrop is clicked
> **THEN** the modal stays open.

---

### AS-L2-7 — Toast primitive
- **Traces to:** AS-L1-3 · **Priority:** Could
- **Source:** `modal.ts` (`toast`: default/gold/pink variants; auto‑dismiss ≈2200 ms + fade)
- **Requirement:** The shell shall provide a transient toast with neutral, gold (celebratory), and pink
  (gentle) variants that auto‑dismisses after a short interval.

**Acceptance criteria**
> **GIVEN** a gold toast is shown
> **WHEN** ~2.2 seconds pass
> **THEN** it begins to dismiss and is removed shortly after.

---

### AS-L2-8 — Shared mascot and decor primitives
- **Traces to:** AS-L1-3 · **Priority:** Could
- **Source:** `parts.ts` (`mascotSVG`, `starSVG`, `skyDecor`, `avatarHTML`)
- **Requirement:** The shell shall provide reusable mascot, star, avatar, and decorative sky components
  used consistently across screens, with decorative elements hidden from assistive technology.

**Acceptance criteria**
> **GIVEN** any screen using the sky decor
> **WHEN** it renders
> **THEN** the decorative clouds/stars are marked decorative (aria‑hidden) and do not interfere with navigation.

---

### AS-L2-9 — PWA manifest
- **Traces to:** AS-L1-4 · **Priority:** Should
- **Source:** `manifest.webmanifest` (name, short_name, description, `start_url`/`scope` `./`, `standalone`, `portrait`, theme `#5EA8DA`, background `#AFE3F4`, icons incl. 512 maskable)
- **Requirement:** The app shall ship a web manifest declaring a name, standalone display, portrait
  orientation, themed colours, and icons including a maskable 512px icon, so it installs as a home‑screen
  app.

**Acceptance criteria**
> **GIVEN** the built app opened in a supporting browser
> **WHEN** installation is offered
> **THEN** it installs standalone with the app icon and name, opening in portrait.

---

### AS-L2-10 — Service‑worker caching strategy
- **Traces to:** AS-L1-5 · **Priority:** Must
- **Source:** `sw.js` (versioned `CACHE`; install `skipWaiting`; activate purges other caches + `clients.claim`; fetch: GET‑only stale‑while‑revalidate)
- **Requirement:** The service worker shall serve GET requests cache‑first while revalidating in the
  background, ignore non‑GET requests, version its cache, purge previous‑version caches on activation,
  and take control immediately.

**Acceptance criteria**
> **GIVEN** the app has been visited once (assets cached)
> **WHEN** it is reopened offline
> **THEN** previously cached GET responses are served and the app loads.

> **GIVEN** a new cache version activates
> **THEN** caches from prior versions are deleted.

---

### AS-L2-11 — Service‑worker registration policy
- **Traces to:** AS-L1-5 · **Priority:** Should
- **Source:** `main.ts` (register `./sw.js` only in production, on load; errors swallowed)
- **Requirement:** The service worker shall be registered only in production builds, after load, and a
  registration failure shall never surface as an error (offline support is a bonus, not a requirement).

**Acceptance criteria**
> **GIVEN** a production build
> **WHEN** the app loads
> **THEN** the service worker registers.

> **GIVEN** registration fails
> **THEN** no error is surfaced and the app continues to work.

---

### AS-L2-12 — Portable relative paths
- **Traces to:** AS-L1-4 · **Priority:** Should
- **Source:** `vite.config.ts` (`base: './'`); manifest `start_url`/`scope` `./`
- **Requirement:** The built app shall use relative asset paths so it can be hosted from any directory
  or static host without reconfiguration.

**Acceptance criteria**
> **GIVEN** the built app hosted from a sub‑path on a static server
> **WHEN** it is opened
> **THEN** all assets, the manifest, and the service worker resolve correctly.

---

### AS-L2-13 — Kid‑first responsive shell
- **Traces to:** AS-L1-6 · **Priority:** Should
- **Source:** `frontend/src/styles/twinkle.css`, `screens.css` (pastel palette, large rounded controls); `docs/mocks/` design source of truth
- **Requirement:** The presentation shell shall use the product's pastel "sky studio" palette, large
  rounded type and chunky touch targets, one prominent primary action per screen, and shall adapt to
  tablet and phone viewports.

**Acceptance criteria**
> **GIVEN** any primary screen on a tablet
> **WHEN** it renders
> **THEN** it shows one obvious primary action with large, touch‑friendly controls consistent with the design mockups.
