# Song Library — L1 High-Level Requirements

**Subsystem code:** SL
**Specification level:** L1 (capability / high‑level)
**Baseline:** v1.0 · **Status:** Approved
**Detailed requirements:** [L2.md](./L2.md)
**Primary dependencies:** Audio Engine (AE, consumer), Family Server Platform (FS), Grown‑Ups Corner (GC, song editor UI)

---

## 1. Purpose

The Song Library defines what a song *is* in TwinkleTune, ships the built‑in catalogue, and provides
the runtime songbook that every play draws from. Songs are stored as **structured note data** (not
recordings), in a shape that is identical on the client and the family server, so a song authored in
one place is renderable, transposable, and singable everywhere. The library also owns the **invariants**
that keep a song within a child‑singable, well‑formed shape.

## 2. Scope

### In scope

- The canonical song schema (song → phrases → notes) and its derived helpers (range, length, difficulty label).
- The seven bundled public‑domain songs available with zero setup and fully offline.
- Runtime songbook resolution: family server when reachable, else last cached list, else bundled.
- The song validation rule‑set, maintained **identically** on client and server.
- Server‑side song CRUD (create, read, update, delete) with validation and seed handling.
- Browsing and difficulty filtering of the songbook.
- Agreement (seed parity) between the bundled catalogue and the server's seed data.

### Out of scope

- The Grown‑Ups song editor UI (form, preview, save) — **GC**; it *uses* SL's schema and validation.
- Transposition and synthesis — **AE**.
- Per‑song high‑score chips and boards — **HS**; the per‑song "Duet" affordance — **DM**.
- The "In your key" indicator — **VP**.

## 3. Context & dependencies

A song is `{ id, title, emoji, art (1–4), bpm, difficulty (1–3), phrases[] }`, each phrase
`{ lyric, notes[] }`, each note `{ midi, start (beats), dur (beats), syll }`. Because content is note
data, the same object round‑trips through synthesis (AE), transposition (VP), scoring (SR), the server
JSON column (FS), and the offline cache. The invariants are duplicated in
`frontend/apps/game/src/songs/types.ts` and `backend/.../SongValidator.cs` by design, so the client editor
rejects exactly what the server would reject.

## 4. High-level requirements

| ID | Requirement | Priority | Rationale |
|----|-------------|----------|-----------|
| **SL-L1-1** | The system shall represent every song as structured note data in a single canonical shape shared by the client and the family server. | Must | One shape enables artefact‑free synthesis, offline caching, and server round‑tripping without translation. |
| **SL-L1-2** | The system shall ship a catalogue of seven public‑domain songs that are available immediately, fully offline, and with no server or setup. | Must | Offline‑first (P2): a child can sing on first launch with no network and no configuration. |
| **SL-L1-3** | The system shall resolve the runtime songbook from the family server when reachable, otherwise from the last cached list, otherwise from the bundled catalogue, and shall never require the network for solo play. | Must | Progressive enhancement: server content is additive, never a dependency. |
| **SL-L1-4** | The system shall enforce a single set of song invariants that keep every stored song well‑formed and child‑singable, applied identically on the client and the server. | Must | A song that saves must be guaranteed renderable and singable; divergent rules would let the server accept songs the client cannot play. |
| **SL-L1-5** | The system shall let a singer browse the songbook and filter it by difficulty. | Should | Discovery for a child who cannot read long lists; difficulty framing supports gradual bravery. |
| **SL-L1-6** | The system shall support server‑side creation, update, and deletion of songs, returning friendly validation feedback and distinguishing built‑in (seed) songs. | Must | Grown‑ups extend the songbook; validation and seed handling protect the family's content. |
| **SL-L1-7** | The bundled catalogue and the server's seed data shall be kept note‑for‑note in agreement. | Should | The offline bundle and the server must present the same seven songs so switching connectivity is seamless. |

## 5. Assumptions & constraints

- Child‑singable base range for notes: MIDI 48–84 (C3–C6); melody span ≤ 16 semitones.
- Tempo 40–220 BPM; art style 1–4; difficulty 1 (Easy), 2 (Medium), 3 (Brave); title ≤ 80 characters.
- Bundled song ids are slugs (e.g. `twinkle`); server song ids are GUIDs.
- The offline songbook cache key is `twinkletune:songs-cache` in `localStorage`.
