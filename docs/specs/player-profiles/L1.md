# Player Profiles — L1 High-Level Requirements

**Subsystem code:** PP
**Specification level:** L1 (capability / high‑level)
**Baseline:** v1.0 · **Status:** Approved
**Detailed requirements:** [L2.md](./L2.md)
**Primary dependencies:** Family Server Platform (FS), Rewards & Progression (RP), Voice Personalization (VP), Grown‑Ups Corner (GC), Family High Scores (HS)

---

## 1. Purpose

Player Profiles lets a family share the app while each singer keeps her own identity and progress. A
profile has a name and either a picked avatar or an uploaded photo; the active singer's identity re‑keys
the entire app so her songs, her voice range, her sparkles, and her badges are the ones in play.
Profiles are created at first run and, when a family server is present, are linked to a server `Singer`
so they follow the child across devices; without a server, a single local‑only profile still works.

## 2. Scope

### In scope

- The client profile model and per‑singer namespacing of on‑device state.
- Switching the active singer and re‑pointing the whole app at her data.
- First‑run onboarding: create a profile, optionally link it to the family server, choose landing.
- A one‑time migration that adopts pre‑profiles progress into the first server profile.
- Avatars as reusable, grown‑up‑curated identities (emoji + name), with CRUD.
- Profile photos: bounded upload, storage, and display in place of the avatar.
- Server‑side singer CRUD with validation; cascade behaviour on deletion.
- Graceful offline behaviour (solo play on the local profile).

### Out of scope

- Capturing the voice range (a profile field) — **VP**; mic latency (a device field) — **GC**.
- The reward data stored per profile — **RP** (PP owns the namespacing; RP owns the contents).
- Family high scores keyed by singer — **HS** (PP owns the singer; HS owns the scores).
- The parent gate that guards profile deletion — **GC** (PP invokes it).

## 3. Context & dependencies

On the client, the active singer id is stored under `twinkletune:active-singer`, and each singer's state
blob lives under `twinkletune:v1:{singerId}`. Switching a singer swaps the store's key and merges the
server's view of that singer into the local profile. On the server, a `Singer` holds name, optional
avatar, optional photo file name, optional voice range, and creation time; deleting a singer removes her
photo and cascades her high scores.

## 4. High-level requirements

| ID | Requirement | Priority | Rationale |
|----|-------------|----------|-----------|
| **PP-L1-1** | The system shall support multiple switchable singer profiles, each with a name and either a picked avatar or an uploaded photo. | Must | Two (or more) siblings share a device and each deserves her own identity. |
| **PP-L1-2** | The system shall namespace all on‑device progress per profile and, on switching, re‑point the entire app at the active singer's data. | Must | Progress must never bleed between siblings; switching must be total and instant. |
| **PP-L1-3** | The system shall create a profile at first run and link it to the family server when reachable, otherwise keep it local‑only, without blocking play. | Must | Onboarding must work online or offline; server linking is additive (P2). |
| **PP-L1-4** | The system shall manage avatars (emoji + name) as reusable identities that grown‑ups can create, edit, and delete. | Should | A curated, friendly avatar set gives children safe identity choices. |
| **PP-L1-5** | The system shall support a real profile photo, bounded by size and type, shown in place of the avatar where appropriate. | Could | A photo makes the profile feel personal; bounds and on‑premises storage keep it safe (P3). |
| **PP-L1-6** | The system shall preserve pre‑existing progress when profiles are introduced, via a one‑time migration into the first profile that claims it. | Should | An existing solo player must not lose sparkles or badges when the family server arrives. |
| **PP-L1-7** | The system shall support server‑side singer create/read/update/delete with validation, removing a deleted singer's photo and cascading her family scores. | Must | Clean lifecycle management with no orphaned photos or scores. |
| **PP-L1-8** | The system shall degrade gracefully when the server is unavailable, continuing solo play on the device profile. | Must | Offline‑first (P2). |

## 5. Assumptions & constraints

- Singer name: required, ≤ 30 characters; a captured range must have high above low.
- Photo: ≤ 2 MB; JPEG, PNG, or WebP only; stored on the server's disk as `{singerId}.{ext}`.
- Default avatar emoji is 🦄; onboarding offers 🦄 🐱 🐸 🦊; the server seeds eight avatars.
- A blank onboarding name defaults to "Superstar".
- Client keys: active singer `twinkletune:active-singer`; per‑singer blob `twinkletune:v1:{singerId}`.
