## 2. Detailed requirements

### PP-L2-1 — Client profile model
- **Traces to:** PP-L1-1 · **Priority:** Must
- **Source:** `store.ts` (`Profile`: name, avatar, range, latencyMs, singerId?, avatarId?, photoUrl?)
- **Requirement:** A profile shall hold the singer's name, chosen avatar emoji, optional voice range,
  device mic latency, and — when server‑linked — the server singer id, avatar id, and photo URL.

**Acceptance criteria**
> **GIVEN** a server‑linked singer with a photo
> **WHEN** her profile is materialised on the client
> **THEN** it carries her name, avatar, range, singer id, avatar id, and photo URL.

---

### PP-L2-2 — Per‑singer storage namespacing
- **Traces to:** PP-L1-2 · **Priority:** Must
- **Source:** `store.ts` (`profileKey(id) = 'twinkletune:v1:{id}'`; active id at `twinkletune:active-singer`)
- **Requirement:** Each singer's on‑device state shall be stored under a per‑singer key, and the active
  singer id shall be persisted separately, so two singers' data never mix.

**Acceptance criteria**
> **GIVEN** two singers A and B
> **WHEN** each records plays while active
> **THEN** A's sparkles/badges live under A's key and B's under B's key, with no cross‑contamination.

---

### PP-L2-3 — Switching the active singer
- **Traces to:** PP-L1-2 · **Priority:** Must
- **Source:** `profile.ts` (`activateSinger` → `setActiveSingerId`, `store.switchKey`, `applySingerToProfile`); `profiles.ts` (navigate home if range else voice)
- **Requirement:** Selecting a singer shall set her as active, switch the store to her namespace, merge
  the server's view into her local profile, and route to home (if she has a range) or to voice setup.

**Acceptance criteria**
> **GIVEN** singer B is chosen from the picker
> **WHEN** activation runs
> **THEN** the app's state switches to B's namespace, B's name/avatar/range populate the profile, and the app navigates to home when B has a range or to voice setup otherwise.

---

### PP-L2-4 — One‑time legacy migration
- **Traces to:** PP-L1-6 · **Priority:** Should
- **Source:** `store.ts` (`adoptLegacyState`: moves `twinkletune:v1` into the first `twinkletune:v1:{id}` that claims it)
- **Requirement:** The first profile to be activated shall adopt any pre‑profiles state blob so that
  earlier solo progress (sparkles, badges) is preserved, and the legacy blob shall then be removed.

**Acceptance criteria**
> **GIVEN** existing pre‑profiles state and no per‑singer blob yet
> **WHEN** the first singer is activated
> **THEN** the legacy state becomes that singer's state and the legacy key is cleared.

> **GIVEN** the target singer already has a per‑singer blob
> **THEN** the legacy blob is not adopted (no overwrite).

---

### PP-L2-5 — First‑run profile creation
- **Traces to:** PP-L1-3 · **Priority:** Must
- **Source:** `welcome.ts` (name → `'Superstar'` if blank; `AVATARS = ['🦄','🐱','🐸','🦊']`; navigate home if range else voice)
- **Requirement:** The welcome screen shall collect a name and a chosen avatar and create a profile; a
  blank name shall default to "Superstar"; after creation it shall route to voice setup (or home if a
  range already exists).

**Acceptance criteria**
> **GIVEN** the welcome screen with an empty name and the default avatar
> **WHEN** the child taps the start action
> **THEN** a profile named "Superstar" with the default avatar is created and the app navigates to voice setup.

---

### PP-L2-6 — Server linking with offline fallback
- **Traces to:** PP-L1-3 · **Priority:** Should
- **Source:** `welcome.ts` (if no `singerId` and `serverOnline()`: match avatar by emoji, `api.singers.create`, `activateSinger`; catch → local‑only)
- **Requirement:** On creating a profile with no server link, if the server is reachable the system
  shall create a corresponding server singer (matching the chosen avatar by emoji) and activate it;
  any failure shall silently leave the profile local‑only, and play shall continue either way.

**Acceptance criteria**
> **GIVEN** onboarding completes while the server is reachable
> **WHEN** linking runs
> **THEN** a server singer is created, the profile is linked and activated, and its avatar matches the chosen emoji.

> **GIVEN** onboarding completes while the server is unreachable (or linking errors)
> **THEN** the profile remains local‑only and onboarding still succeeds.

---

### PP-L2-7 — Server singer entity and DTO
- **Traces to:** PP-L1-1 · **Priority:** Must
- **Source:** `Singer.cs`; `SingerDto`; `Mapping.cs`
- **Requirement:** A server singer shall hold id, name, optional avatar (id + emoji), optional photo
  file name, optional range low/high, and creation time; its DTO shall expose id, name, avatar id,
  avatar emoji, a has‑photo flag, and range.

**Acceptance criteria**
> **GIVEN** a singer with an avatar and a photo
> **WHEN** it is returned as a DTO
> **THEN** the DTO includes the avatar emoji and `hasPhoto = true`.

---

### PP-L2-8 — Singer CRUD endpoints
- **Traces to:** PP-L1-7 · **Priority:** Must
- **Source:** `SingersController.cs`; `SingerService.cs`
- **Requirement:** The server shall expose `GET /api/singers`, `GET /api/singers/{id}`,
  `POST /api/singers`, `PUT /api/singers/{id}`, `DELETE /api/singers/{id}`, returning 200/201/204 on
  success and 404 for a missing singer; the name shall be trimmed and creation time set on create.

**Acceptance criteria**
> **GIVEN** a valid singer body
> **WHEN** it is POSTed
> **THEN** the server responds 201 with the stored singer.

> **GIVEN** a non‑existent id
> **WHEN** it is updated or deleted
> **THEN** the server responds 404.

---

### PP-L2-9 — Singer validation
- **Traces to:** PP-L1-7 · **Priority:** Must
- **Source:** `SingerService.Validate` (name required, ≤30; high above low)
- **Requirement:** The server shall reject a singer with a blank name, a name over 30 characters, or a
  range whose high note is not above its low note, returning a friendly error.

**Acceptance criteria**
> **GIVEN** a singer body with a blank name
> **WHEN** it is submitted
> **THEN** it is rejected with "Every singer needs a name.".

> **GIVEN** a singer body with `rangeHigh ≤ rangeLow`
> **THEN** it is rejected with "The high note must be above the low note.".

---

### PP-L2-10 — Singer ordering and avatar inclusion
- **Traces to:** PP-L1-7 · **Priority:** Could
- **Source:** `Repositories.cs` (`SingerRepository`: ordered by `CreatedAt`, includes `Avatar`)
- **Requirement:** The singer list shall be ordered by creation time and shall include each singer's
  avatar so the picker can render emoji without extra calls.

**Acceptance criteria**
> **GIVEN** several singers created over time
> **WHEN** the list is fetched
> **THEN** they appear oldest‑first and each includes its avatar emoji.

---

### PP-L2-11 — Avatar CRUD and validation
- **Traces to:** PP-L1-4 · **Priority:** Should
- **Source:** `AvatarsController.cs`; `AvatarService.cs` (emoji required, name required ≤30); `seed-data.json` (8 seeded avatars)
- **Requirement:** The server shall expose `GET/POST /api/avatars` and `PUT/DELETE /api/avatars/{id}`,
  validating that an avatar has a non‑empty emoji and a non‑empty name ≤ 30 characters; a fresh server
  shall seed eight avatars.

**Acceptance criteria**
> **GIVEN** an avatar body with an empty emoji
> **WHEN** it is submitted
> **THEN** it is rejected with "An avatar needs an emoji.".

> **GIVEN** a freshly initialised server
> **THEN** eight avatars are present.

---

### PP-L2-12 — Avatar deletion detaches singers
- **Traces to:** PP-L1-4 · **Priority:** Should
- **Source:** `AppDbContext.cs` (Singer→Avatar FK `OnDelete(SetNull)`)
- **Requirement:** Deleting an avatar shall set the avatar reference of any singer using it to null
  rather than deleting the singer.

**Acceptance criteria**
> **GIVEN** a singer using avatar X
> **WHEN** avatar X is deleted
> **THEN** the singer remains, with no avatar, and is unaffected otherwise.

---

### PP-L2-13 — Profile photo upload constraints and storage
- **Traces to:** PP-L1-5 · **Priority:** Could
- **Source:** `SingersController.SetPhoto` (multipart, ≤2 MB, `PhotoStorage.IsSupported`); `PhotoStorage.cs` (saves `{id}.{ext}`, replaces prior, path‑traversal safe)
- **Requirement:** The server shall accept a profile photo only as multipart form data, ≤ 2 MB, of type
  JPEG/PNG/WebP; it shall store it as `{singerId}.{ext}`, replacing any previous photo, and shall serve
  it back safely (no path traversal).

**Acceptance criteria**
> **GIVEN** a 1 MB JPEG uploaded for a singer
> **WHEN** the upload completes
> **THEN** the singer's photo is stored, `hasPhoto` becomes true, and any previous photo is replaced.

> **GIVEN** a 3 MB upload, or a GIF
> **THEN** the request is rejected with a friendly size/type message.

---

### PP-L2-14 — Photo display precedence
- **Traces to:** PP-L1-5 · **Priority:** Could
- **Source:** `parts.ts` (`avatarHTML`: photo when `photoUrl` else emoji); `profiles.ts` (photo with cache‑buster); `me.ts` (always emoji)
- **Requirement:** Where a photo exists it shall be shown in place of the avatar emoji (home, picker),
  with a cache‑buster on the picker; the progress ("Me") screen shall always show the emoji avatar.

**Acceptance criteria**
> **GIVEN** a profile with a photo URL
> **WHEN** the home avatar renders
> **THEN** the photo is shown instead of the emoji.

> **GIVEN** the same profile
> **WHEN** the "Me" screen renders
> **THEN** the emoji avatar is shown.

---

### PP-L2-15 — Singer deletion cleanup, cascade, and parent gate
- **Traces to:** PP-L1-7 · **Priority:** Must
- **Source:** `SingerService.DeleteAsync` (deletes photo file); `AppDbContext.cs` (HighScore→Singer FK Cascade); `profiles.ts` (delete behind `parentGate`)
- **Requirement:** Deleting a singer shall remove her stored photo and cascade‑delete her high scores;
  in the UI, deletion shall be guarded by the parent gate and confirmed.

**Acceptance criteria**
> **GIVEN** a singer with a photo and family high scores
> **WHEN** she is deleted on the server
> **THEN** her photo file is removed and her high scores are deleted.

> **GIVEN** the profiles screen
> **WHEN** a grown‑up initiates a singer deletion
> **THEN** the parent gate must be passed and a confirmation accepted before deletion proceeds.

---

### PP-L2-16 — Profiles picker and offline handling
- **Traces to:** PP-L1-8 · **Priority:** Should
- **Source:** `profiles.ts` (picker cards; active tag; offline "keep singing solo" panel)
- **Requirement:** The profiles screen shall list singers as pickable cards (marking the active one),
  offer creating a new singer, and — when the server is unreachable — present a "keep singing solo"
  path instead of an error.

**Acceptance criteria**
> **GIVEN** a reachable server with two singers
> **WHEN** the picker renders
> **THEN** both are shown as cards, the active one is marked, and a "new singer" affordance is present.

> **GIVEN** the server is unreachable
> **WHEN** the picker loads
> **THEN** it shows a friendly "keep singing solo" panel that returns to home.

---

### PP-L2-17 — Profile push to server
- **Traces to:** PP-L1-8 · **Priority:** Should
- **Source:** `profile.ts` (`pushProfileToServer`: name, avatarId, range; fire‑and‑forget)
- **Requirement:** When linked, local changes to the profile's name, avatar, and range shall be pushed
  to the server, and a push that fails while offline shall not surface an error and shall reconcile on
  a later successful update.

**Acceptance criteria**
> **GIVEN** a server‑linked profile whose range was just captured, with the server reachable
> **WHEN** the push runs
> **THEN** the server singer reflects the new range.

> **GIVEN** the server is unreachable during a push
> **THEN** no error is surfaced and the local profile is unaffected.
