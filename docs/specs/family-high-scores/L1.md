# Family High Scores — L1 High-Level Requirements

**Subsystem code:** HS
**Specification level:** L1 (capability / high‑level)
**Baseline:** v1.0 · **Status:** Approved
**Detailed requirements:** [L2.md](./L2.md)
**Primary dependencies:** Family Server Platform (FS), Player Profiles (PP), Song Library (SL), Scoring & Results (SR)

---

## 1. Purpose

Family High Scores gives a household a private, motivating "who's the family champion of this song?"
without ever ranking a child against a stranger. The server keeps exactly one best result per singer
per song, updates it only when a new performance genuinely beats it, and serves per‑song and per‑singer
boards. It is deliberately **family‑scoped** — there are no global leaderboards — in keeping with the
product's confidence‑first ethos and children's‑privacy posture.

## 2. Scope

### In scope

- One best result per (song, singer): stars, accuracy, sparkles, max streak, and when it was achieved.
- Upsert‑if‑better submission semantics and an "improved" signal.
- Ranking (stars, then accuracy) for per‑song and per‑singer boards.
- Submission validation and referential integrity (song and singer must exist).
- The in‑app per‑song board and the "new family record" celebration.
- Availability gating: boards appear only when the family server is reachable.

### Out of scope

- Deciding *when* the client submits a score and computing the values — **SR** (submits) / **SG** (plays).
- The on‑device rewards (sparkles, badges, streaks) which are separate and per‑profile — **RP**.
- Singer identity and photos surfaced on the board — **PP**.
- The server platform, persistence, and cascade wiring — **FS** (HS defines the semantics; FS hosts them).

## 3. Context & dependencies

After a scored run by a server‑linked singer on a server song, the results screen submits
`{ songId, singerId, stars, accuracy, sparkles, maxStreak }`. The server compares against the stored
best by stars first, then accuracy, and replaces it only if beaten. Boards join the singer's name and
avatar/photo for display. High scores cascade‑delete with their song or singer.

## 4. High-level requirements

| ID | Requirement | Priority | Rationale |
|----|-------------|----------|-----------|
| **HS-L1-1** | The system shall maintain exactly one best result per singer per song, recording stars, accuracy, sparkles, max streak, and the achievement time. | Must | A single, meaningful "personal/family best" per song, not a history of every attempt. |
| **HS-L1-2** | The system shall accept a submission and store it only if it beats the stored best (stars first, then accuracy), reporting whether the record improved. | Must | Upsert‑if‑better keeps boards showing genuine bests and drives the "new record" moment. |
| **HS-L1-3** | The system shall rank scores by stars, then accuracy, for both per‑song and per‑singer boards. | Should | A single, consistent ordering that matches how a best is defined. |
| **HS-L1-4** | The system shall validate a submission's values and require that the referenced song and singer exist. | Must | Guards board integrity against malformed or dangling submissions. |
| **HS-L1-5** | The system shall present a per‑song family board in the app, available only when the family server is reachable. | Should | Boards are a server feature; offline the app cleanly hides them (P2). |
| **HS-L1-6** | High scores shall remain family‑scoped and private, with no global leaderboards. | Must | Children's safety and the confidence‑first ethos (ADR‑0001): no ranking against strangers. |

## 5. Assumptions & constraints

- Uniqueness is enforced on (SongId, SingerId).
- A submission is valid only for stars 0–3 and accuracy 0–1.
- "Beaten by" means `stars > best.stars` OR (`stars == best.stars` AND `accuracy > best.accuracy`).
- High scores are stored only on the family server (never on device); the server is LAN‑only (FS).
