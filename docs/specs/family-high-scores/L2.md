## 2. Detailed requirements

### HS-L2-1 — One best per singer per song
- **Traces to:** HS-L1-1 · **Priority:** Must
- **Source:** `AppDbContext.cs` (unique index on `{SongId, SingerId}`)
- **Requirement:** The store shall permit at most one high‑score record per (song, singer) pair.

**Acceptance criteria**
> **GIVEN** an existing high score for singer S on song G
> **WHEN** S submits again for G
> **THEN** no second record is created; the single record is updated in place (or left unchanged).

---

### HS-L2-2 — Submission value validation
- **Traces to:** HS-L1-4 · **Priority:** Must
- **Source:** `HighScoreService.SubmitAsync` (stars 0–3, accuracy 0–1)
- **Requirement:** The server shall reject a submission whose stars are outside 0–3 or whose accuracy
  is outside 0–1, with a friendly error.

**Acceptance criteria**
> **GIVEN** a submission with stars = 5
> **THEN** it is rejected with "Stars must be between 0 and 3.".

> **GIVEN** a submission with accuracy = 1.5
> **THEN** it is rejected with "Accuracy must be between 0 and 1.".

---

### HS-L2-3 — Referential integrity
- **Traces to:** HS-L1-4 · **Priority:** Must
- **Source:** `HighScoreService.SubmitAsync` (song exists; singer exists)
- **Requirement:** The server shall reject a submission that references a non‑existent song or singer.

**Acceptance criteria**
> **GIVEN** a submission for an unknown song id
> **THEN** it is rejected with "That song doesn't exist.".

> **GIVEN** a submission for an unknown singer id
> **THEN** it is rejected with "That singer doesn't exist.".

---

### HS-L2-4 — Upsert‑if‑better comparison
- **Traces to:** HS-L1-2 · **Priority:** Must
- **Source:** `HighScore.IsBeatenBy` (stars, then accuracy); `HighScoreService.SubmitAsync`; `HighScoreServiceTests`
- **Requirement:** An existing best shall be replaced only when the new result beats it — more stars,
  or equal stars with higher accuracy.

**Acceptance criteria**
> **GIVEN** a best of 2 stars / 0.70
> **WHEN** a submission of 3 stars / 0.60 arrives
> **THEN** the record is replaced (more stars wins despite lower accuracy).

> **GIVEN** a best of 2 stars / 0.70
> **WHEN** a submission of 2 stars / 0.65 arrives
> **THEN** the record is left unchanged.

---

### HS-L2-5 — New‑record insertion
- **Traces to:** HS-L1-2 · **Priority:** Must
- **Source:** `HighScoreService.SubmitAsync` (no existing → add fresh, `Improved = true`)
- **Requirement:** A first submission for a (song, singer) pair shall create the record and report the
  result as improved, stamping the achievement time.

**Acceptance criteria**
> **GIVEN** no prior score for singer S on song G
> **WHEN** S submits any valid result
> **THEN** a record is created, `improved` is true, and the achievement time is set.

---

### HS-L2-6 — Not‑improved outcome
- **Traces to:** HS-L1-2 · **Priority:** Must
- **Source:** `HighScoreService.SubmitAsync` (not beaten → return existing, `Improved = false`)
- **Requirement:** A submission that does not beat the stored best shall leave it unchanged and report
  the result as not improved, returning the existing best.

**Acceptance criteria**
> **GIVEN** a stored best that is not beaten by the submission
> **WHEN** the submission is processed
> **THEN** the response reports `improved = false` and returns the unchanged best.

---

### HS-L2-7 — Board ordering
- **Traces to:** HS-L1-3 · **Priority:** Should
- **Source:** `HighScoreService.GetForSongAsync` / `GetForSingerAsync` (order by stars desc, then accuracy desc)
- **Requirement:** Per‑song and per‑singer boards shall be ordered by stars descending, then accuracy
  descending.

**Acceptance criteria**
> **GIVEN** three scores of (3★,0.9), (3★,0.95), (2★,0.99)
> **WHEN** the song board is fetched
> **THEN** the order is (3★,0.95), (3★,0.9), (2★,0.99).

---

### HS-L2-8 — Board and submission endpoints
- **Traces to:** HS-L1-5 · **Priority:** Must
- **Source:** `HighScoresController.cs` (POST `/api/highscores`; GET `/api/songs/{id}/highscores`; GET `/api/singers/{id}/highscores`)
- **Requirement:** The server shall expose a submission endpoint and per‑song and per‑singer board
  endpoints.

**Acceptance criteria**
> **GIVEN** a valid submission
> **WHEN** it is POSTed to `/api/highscores`
> **THEN** the response includes the `improved` flag and the resulting score.

> **GIVEN** a song with scores
> **WHEN** `GET /api/songs/{id}/highscores` is called
> **THEN** the ranked board for that song is returned.

---

### HS-L2-9 — Board DTO includes singer identity
- **Traces to:** HS-L1-1 · **Priority:** Should
- **Source:** `HighScoreDto`; `Mapping.cs` (singer name defaults to "Singer" if missing; avatar emoji; has‑photo)
- **Requirement:** Each board entry shall carry the singer's name, avatar emoji, and a has‑photo flag,
  alongside stars, accuracy, sparkles, max streak, and achievement time.

**Acceptance criteria**
> **GIVEN** a score by a singer with an avatar
> **WHEN** the board is returned
> **THEN** the entry includes the singer's name and avatar emoji.

---

### HS-L2-10 — Cascade with song and singer
- **Traces to:** HS-L1-6 · **Priority:** Should
- **Source:** `AppDbContext.cs` (HighScore→Song and HighScore→Singer FKs `OnDelete(Cascade)`)
- **Requirement:** A high score shall be deleted automatically when its song or its singer is deleted.

**Acceptance criteria**
> **GIVEN** a song with several high scores
> **WHEN** the song is deleted
> **THEN** its high scores are removed too.

---

### HS-L2-11 — Client submission eligibility
- **Traces to:** HS-L1-5 · **Priority:** Should · **See also:** SR‑L2‑15
- **Source:** `results.ts` (submit only when scored, server‑linked singer, server song)
- **Requirement:** The client shall submit a high score only for a scored run by a server‑linked singer
  on a server (GUID) song, and shall never submit for no‑mic runs, local‑only profiles, or bundled
  songs.

**Acceptance criteria**
> **GIVEN** a scored run by a server‑linked singer on a server song
> **THEN** a submission is sent.

> **GIVEN** a bundled song id or a local‑only profile
> **THEN** no submission is sent.

---

### HS-L2-12 — Per‑song board UI
- **Traces to:** HS-L1-5 · **Priority:** Should
- **Source:** `songs.ts` (`showBoard`: medals 🥇🥈🥉 then numbers; singer avatar; stars glyphs; accuracy %; empty and error states)
- **Requirement:** The per‑song board shall list ranked entries with a medal/position, the singer's
  avatar and name, a star glyph rendering, and an accuracy percentage; it shall show a friendly empty
  state when there are no scores and a friendly message when the server is unreachable.

**Acceptance criteria**
> **GIVEN** a song with three scores
> **WHEN** the board opens
> **THEN** the top three show 🥇/🥈/🥉, each with avatar, name, stars, and accuracy percentage.

> **GIVEN** a song with no scores
> **THEN** the board shows "No scores yet — be the first! ⭐".

> **GIVEN** the server is unreachable
> **THEN** the board shows "Scores need the family server 📡".

---

### HS-L2-13 — Board availability gating
- **Traces to:** HS-L1-5 · **Priority:** Should
- **Source:** `songs.ts` (board button only when songbook is live; board opens only for server song ids)
- **Requirement:** The per‑song board affordance shall appear only when the songbook is served live and
  shall open only for server (GUID) song ids.

**Acceptance criteria**
> **GIVEN** the songbook is offline (cached/bundled)
> **THEN** no board button is shown on song cards.

---

### HS-L2-14 — New family record celebration
- **Traces to:** HS-L1-2 · **Priority:** Should · **See also:** SR‑L2‑15
- **Source:** `results.ts` (on `improved` → "🏆 New family record!")
- **Requirement:** When a submission improves the family record, the app shall celebrate it with a
  "New family record!" message.

**Acceptance criteria**
> **GIVEN** a submission that beats the prior best
> **WHEN** the server reports `improved = true`
> **THEN** the app shows a "🏆 New family record!" celebration.

---

### HS-L2-15 — Family‑scoped, no global leaderboard
- **Traces to:** HS-L1-6 · **Priority:** Must
- **Source:** ADR‑0001 / ADR‑0002 (family‑scoped only); server has no cross‑family board endpoint
- **Requirement:** High scores shall be scoped to the single family server; the product shall expose no
  global or cross‑family leaderboard.

**Acceptance criteria**
> **GIVEN** the full API surface
> **WHEN** it is inspected
> **THEN** there is no endpoint that ranks singers across families or exposes scores beyond the local server.
