# Duet Multiplayer — L1 High-Level Requirements

**Subsystem code:** DM
**Specification level:** L1 (capability / high‑level)
**Baseline:** v1.0 · **Status:** Approved
**Detailed requirements:** [L2.md](./L2.md)
**Primary dependencies:** Family Server Platform (FS), Player Profiles (PP), Singing Gameplay (SG), Scoring & Results (SR), Song Library (SL)
**Governing decisions:** ADR‑0001 (family‑scoped duets, not an online platform), ADR‑0002 (in‑memory rooms)

---

## 1. Purpose

Duet Multiplayer lets two singers — typically two sisters — perform the same song at the same time on
two devices and cheer each other on. It is built as **Family Duet rooms**, not an online platform:
short‑lived room codes, no accounts, exactly two players, and cooperative‑first results. Only tiny score
events cross the network; each device still hears and scores itself. The framing leads with shared
"family sparkles" so the mode builds connection rather than rivalry.

## 2. Scope

### In scope

- Creating and joining an ephemeral, code‑based, two‑player room.
- Relaying small score events (landed count, streak, sparkles, note index) and finish summaries between
  the two clients — never audio.
- A synchronised start based on a server timestamp plus a count‑in to absorb LAN clock skew.
- Live opponent progress display during the song and a cooperative combined‑result at the end.
- Presence handling: join, leave, disconnect, room closure, and idle‑room expiry.
- Gating on a family server and a server‑linked profile, with graceful fallback.

### Out of scope

- The actual singing render loop, pitch, and local scoring — **SG / AE / SR** (DM feeds them the
  opponent overlay and the synchronised start).
- Persisting anything about the duet — rooms are in‑memory only (ADR‑0002).
- Global/cross‑family competition — explicitly excluded (ADR‑0001).

## 3. Context & dependencies

The family server hosts a SignalR hub (`/hubs/duet`) backed by an in‑memory room registry. A client
creates a room and receives a 4‑letter code; a second client joins with it. When both are present, a
player starts a song; the server broadcasts a `SongStarted` with a near‑future start time. During the
song, each client throttles its score to one tick per finalised note; the hub relays it to the other.
When both finish, the hub emits a combined result whose headline is the shared sparkle total.

## 4. High-level requirements

| ID | Requirement | Priority | Rationale |
|----|-------------|----------|-----------|
| **DM-L1-1** | The system shall let two singers on two devices sing the same song simultaneously in a shared private room. | Must | The core "sing together" value that solo play cannot offer. |
| **DM-L1-2** | Rooms shall be ephemeral, joined by a short human‑readable code, limited to exactly two players, and require no accounts. | Must | Kid‑safe, low‑identity, Kahoot‑style joining (ADR‑0001); two‑sister scope. |
| **DM-L1-3** | The system shall relay only small score events and finish summaries between clients; scoring shall remain on each client and audio shall never be streamed. | Must | Privacy (P3) and technical fit: score events are tiny; audio streaming is out of scope (ADR‑0001). |
| **DM-L1-4** | The system shall synchronise the start of a duet using a server‑issued near‑future start time plus a count‑in, to absorb clock skew between devices. | Should | Fairness of a shared start on mixed Wi‑Fi/wired devices. |
| **DM-L1-5** | The system shall show each singer the opponent's live progress during the song and announce when the opponent finishes. | Should | Presence and mutual encouragement are what make singing together fun. |
| **DM-L1-6** | The system shall present cooperative‑first combined results, leading with shared family sparkles and de‑emphasising winning/losing. | Must | Protects confidence and sibling harmony (ADR‑0001 risk mitigation). |
| **DM-L1-7** | The system shall require a family server and a server‑linked profile for duets and shall degrade gracefully (route to solo or profile setup) when unavailable. | Must | Duets are inherently server‑ and identity‑dependent; the fallback must be kind (P2). |
| **DM-L1-8** | The system shall handle presence changes (join, leave, disconnect) and reconnection gracefully, and shall expire idle rooms. | Should | Robustness against dropped devices and abandoned rooms. |

## 5. Assumptions & constraints

- Room codes are 4 letters from an unambiguous alphabet (no I, L, or O).
- Maximum two players per room; rooms expire after 30 idle minutes and are never persisted.
- The synchronised start time is set ≈3 seconds in the future; a 4‑beat count‑in further absorbs skew.
- Score ticks carry `{ landed, streak, sparkles, noteIdx }`; the client throttles to one per finalised note.
